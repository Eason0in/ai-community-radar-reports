## 2. 痛點雷達：最近值得解的麻煩事

這段混合開發者工作流與一般軟體使用痛點。重點不是列現有工具，而是找還有機會被 MCP / agent 工作流改善的地方。

### 1. AI 產生碼讓 Review 變成風險判讀問題

| 欄位 | 內容 |
| --- | --- |
| 類型 | 開發者工作流 |
| 誰會痛 | Tech lead、reviewer、平台工程團隊 |
| 麻煩點 | AI 寫碼速度變快，但 reviewer 不知道哪些 diff 是高風險、哪些缺測、哪些 API 可能是模型幻覺。 |
| 現在通常怎麼處理 | 靠作者自述、人工掃 diff、全量跑 CI；速度慢且 reviewer 負擔集中在少數資深工程師。 |
| 為什麼適合 MCP | MCP 可以串 Git diff、coverage、測試紀錄、issue 背景與靜態分析，把 PR 先整理成 agent 可讀的風險包。 |
| 參考依據 | Stack Overflow 提到 AI 工具信任落差；Sonar 2026 也把 AI 產碼後的 code quality 與 technical debt 治理列為核心議題。 |

### 2. Agent 做事前，人還要手動搬運上下文

| 欄位 | 內容 |
| --- | --- |
| 類型 | 開發者工作流 |
| 誰會痛 | 使用 Codex、Claude Code、Cursor 的工程師 |
| 麻煩點 | 真正有用的上下文分散在 issue、Slack、PR、runbook、logs、feature flags；每次都要人工複製貼上。 |
| 現在通常怎麼處理 | 把連結丟給 agent、手動摘錄、或讓 agent 自己亂找；結果容易漏資料或花太多 token。 |
| 為什麼適合 MCP | MCP 適合把多來源上下文打包成標準 resources，讓 agent 開始工作前先拿到同一份任務包。 |
| 參考依據 | MCP 的價值在於把 AI 從 isolated chat 接到可操作的系統與資料來源。 |

### 3. 套件升級風險難判斷，尤其 monorepo 更痛

| 欄位 | 內容 |
| --- | --- |
| 類型 | 開發者工作流 |
| 誰會痛 | 平台工程、前後端維護者、release manager |
| 麻煩點 | Dependabot 類工具會開 PR，但不會充分說明 breaking changes、受影響路徑、應該補哪些測試。 |
| 現在通常怎麼處理 | 人工看 changelog、搜尋 breaking change、猜測測試範圍。 |
| 為什麼適合 MCP | MCP 可以串 package registry、repo usage、lockfile、test map，幫 agent 產出升級風險摘要與測試建議。 |
| 參考依據 | AI coding 讓變更量增加，依賴升級的驗證成本也更需要自動化。 |

### 4. 文件讀完以後，真正要做的事沒有進系統

| 欄位 | 內容 |
| --- | --- |
| 類型 | 一般軟體使用 |
| 誰會痛 | 法務、HR、客服、內部營運 |
| 麻煩點 | 合約、SOP、政策、客訴紀錄裡有待辦與限制，但使用者需要自己拆成任務、提醒與審核步驟。 |
| 現在通常怎麼處理 | 人工摘要、貼到任務系統、靠 checklist 管控。 |
| 為什麼適合 MCP | MCP 可以把 document parsing、approval workflow、task system 串成可審計的半自動流程。 |
| 參考依據 | 企業導入 AI 的阻力不只是生成答案，而是答案要安全地進入既有工作流。 |

### 5. Agent 權限與 side effects 不透明，企業不敢放手

| 欄位 | 內容 |
| --- | --- |
| 類型 | 一般軟體使用 |
| 誰會痛 | IT、資安、平台團隊、導入 MCP 的企業 |
| 麻煩點 | MCP tool 能讀什麼、能改什麼、是否 destructive、是否會外送資料，常靠 README 或口頭約定。 |
| 現在通常怎麼處理 | 先禁用寫入工具、逐一人工審核 server、或只允許少數白名單。 |

| 參考依據 | MCP 把 AI 連到真實系統後，治理和可審計性會比單純聊天更重要。 |

| 參考依據 | 一般軟體使用痛點常出在跨工具流程斷裂，而 MCP 正好擅長把工具流程串起來。 |

### 1. AI Code Provenance / Review MCP

**目標使用者**

reviewer、tech lead、平台工程團隊

**能做什麼**

分析 PR diff、測試覆蓋、疑似 AI 產生區塊與風險路徑，幫 reviewer 先看到該看哪裡。

**實際可以運用在哪裡**

PR 開出後，agent 呼叫 MCP 產生 review packet：高風險檔案、缺測區塊、可能錯用 API、建議 reviewer。

**解決什麼問題**

降低 AI 產碼造成的 review 不信任與 technical debt 風險。

**MCP tools / resources 可以長這樣**

`analyze_pr_risk`, `map_diff_to_tests`, `explain_uncovered_changes`, `suggest_reviewers`

**MVP**

先支援 GitHub PR + coverage XML + test history，輸出 read-only Markdown comment。

**怎麼驗證有沒有價值**

拿最近 20 個 PR 比對：是否更早抓到缺測、錯誤 API、或 reviewer 實際留言區塊。

**風險與邊界**

不要自動 approve 或改碼；第一版只做風險排序與證據摘要。

**缺口假設 / 競品提醒**

### 5. Context Pack Builder MCP

**目標使用者**

每天使用 coding agent 的工程師與 PM

**能做什麼**

把 issue、PR、Slack thread、runbook、logs、docs 整理成 agent 開工前可讀的 context pack。

**實際可以運用在哪裡**

使用者輸入 ticket id，MCP 回傳 task brief、相關檔案、最近討論、限制條件與驗收標準。

**解決什麼問題**

減少複製貼上與上下文漏失，讓 agent 不需要盲目搜尋。

**MCP tools / resources 可以長這樣**

`build_context_pack`, `list_related_threads`, `fetch_runbook`, `summarize_constraints`

**MVP**

先接 GitHub Issues + Slack permalink + repo README，輸出單一 Markdown resource。

**怎麼驗證有沒有價值**

**風險與邊界**

需要權限邊界與來源引用，避免把不該進任務包的訊息帶入。

**缺口假設 / 競品提醒**

npm 取樣中看到相鄰工具：@mcp-b/webmcp-ts-sdk, @utcp/mcp；要做時應先確認差異化。

SRE、on-call、release owner

**能做什麼**

把事故期間的 deploy、alerts、logs、recent PR、feature flags 彙整成排查 workspace。

**實際可以運用在哪裡**

**解決什麼問題**

縮短事故初期資訊收集時間，減少在多個 dashboard 間切換。

**MCP tools / resources 可以長這樣**

`collect_incident_context`, `build_timeline`, `rank_suspect_changes`, `list_safe_checks`

**MVP**

先做 read-only：GitHub deployments + Datadog/Sentry logs link + LaunchDarkly flag snapshot。

**怎麼驗證有沒有價值**

用過去 incident retro 測試，看能否重建 80% 以上初期 timeline。

**風險與邊界**

不能讓 agent 直接 rollback 或改 flag；第一版只提供 evidence packet。

### 8. Spreadsheet QA MCP

**實際可以運用在哪裡**
