## 3. 新技術、新方法

### 先判斷任務複雜度，再決定 Agent 要「想多久」

- **論文日期：2026-07-14｜性質：arXiv 預印本、作者實驗結果。**
- 論文提出 **E3：Estimate → Execute → Expand**：先估計任務需要的檔案與步驟，用最小上下文執行；只有證據不足或驗證失敗時才擴大搜尋與推理。
- 作者另提出 Agent Cognitive Redundancy Ratio（ACRR）衡量完成任務時有多少多餘認知工作。在 121 個可確定驗證的程式修改任務上，作者回報在保持 100% 成功率下，成本減少 85%、Token 減少 91%、讀取檔案數減少 92%。
- **不要過度解讀：**這是受控 benchmark 與有限的真實 harness 測試；不是所有 repo、模型或長期 Agent 都會得到相同比例。真正可帶走的是「預設最小、失敗再擴張」的控制策略。

來源：[論文摘要與原文入口](https://arxiv.org/abs/2607.13034)

### 從 Hugging Face 事件抽出的 Agent 安全最小框架

1. 把外部資料集、文件與工具回傳值視為不可信輸入，解析與執行分離。
2. 每次工具動作都用身分、資源與意圖重新授權，而不是只靠 system prompt。
3. 為檔案、網路、憑證與可執行工具設 allowlist、最小權限和短效 Token。
4. 限制迭代次數、費用與影響範圍；保留每次工具呼叫、輸入摘要與結果。
5. 遇到異常先停止與輪替憑證，再讓模型協助分流日誌；不要讓同一個 Agent 同時當執行者與唯一稽核者。

這是依官方事件細節整理的防禦性推論，不是 Hugging Face 發布的通用安全標準。

## 4. 社群實戰心得

### 「模型拒答」不是執行期安全邊界

- Reddit 的 AI Governance 討論認為，託管模型因安全護欄拒絕分析攻擊內容，不代表應放寬模型限制；比較可靠的方向是把身分、授權、政策與動作限制放在模型外的 runtime。
- 這與 Hugging Face 官方報告所呈現的問題一致，但該貼文仍是 **社群觀點**，不是對事件的獨立鑑識。

來源：[Reddit 討論](https://www.reddit.com/r/AI_Governance/comments/1uz468g/huggingfaces_aionai_attack_safety_guardrails/)

### Coding Agent 的成本控制：昂貴模型規劃，便宜模型執行，測試決定是否接受

- 一位 Copilot 使用者分享的流程是：高階模型做 plan／review，較便宜模型負責實作與修補；以 `AGENTS.md` 固化規則，並在不同階段開新對話避免上下文腐化。
- 回覆者補上最重要的界線：只有測試通過才接受修改；也有人反映 Copilot 容易增加不必要複雜度或選到過時工具。
- 這套心得與 E3 的「先估、最小執行、失敗再擴張」相容，值得小規模試驗；但它是 **個人經驗，不是模型間的公平成本評測**。

來源：[Reddit：Copilot workflow best practice](https://www.reddit.com/r/GithubCopilot/comments/1uz2z3y/copilot_workflow_best_practice/)

## 5. YouTube 深度整理

### Tech With Tim｜AI Agents Explained - And How to Build One

- **發布日期：2026-07-16｜查核時觀看次數：22,699｜片長：21:33**
- 連結：[YouTube 原片](https://www.youtube.com/watch?v=ZvDkJsKE80k)
- **快速摘要：**Tim 用同一個研究助理需求，解釋 Agent 的核心迴圈，並比較 no-code、low-code、自備 Agent harness 與全程式碼四條實作路線。內容對新手清楚，真正有價值的不是工具名單，而是「控制程度、建置時間與可靠性」的選擇框架。
- **商業揭露：**影片說明欄含 DataCamp、Hostinger、WisprFlow 等聯盟／商業連結，`08:25` 有 DataCamp 段落；作者在逐字稿中表示所提工具選擇不是付費推薦。以下仍將示範心得視為作者觀點。

**內容重點與時間點**

1. `00:52–07:14`：Agent 不是單純聊天機器人，而是「LLM + 工具 + 反覆執行迴圈」。模型提出工具呼叫，由外部程式執行，再把結果送回上下文。
2. `07:15–09:51`：選型不是先問哪個框架最紅，而是先決定要把多少控制權交給平台。
3. `09:52–12:35`：no-code 適合快速驗證與非技術使用者；能很快產出結果，但可控性、可攜性與除錯深度較低。
4. `12:36–17:43`：n8n／Make 類 low-code 工具適合固定、可視化的跨服務流程；OpenClaw、Hermes、Letta 等 harness 提供更多技能、工具或記憶擴充，但設定與維運成本上升。
5. `17:44–21:33`：全程式碼路線用 Python、工具 schema、上下文管理與 loop 取得最大控制；示範提到 LangGraph、Firecrawl 與 GPT-4o，代價是需自行處理錯誤、限制與部署。

**影片示範的工作流程**

1. 定義單一目標，例如「研究某個工具並附來源」。
2. 給 Agent 一個搜尋／擷取工具，而不是一開始塞入所有資料。
3. 讓模型判斷下一個工具呼叫，程式執行後把結果回填上下文。
4. 重複到任務完成；實務上應加最大迭代數、工具 allowlist 與結果驗證。
5. 依需求選層級：快速試驗用 no-code；固定跨系統流程用 low-code；要技能／記憶擴充用 harness；高度客製與可稽核性用 full code。

**作者心得、優缺點與限制**

- 作者認為 no-code 最快、n8n 適合可靠且一致的流程；Hermes 的研究示範耗時較久，但做了較多搜尋與自我修正。
- 優點是以同一需求比較四種抽象層，選型邏輯易懂；缺點是示範不是受控 benchmark，沒有一致的成功率、成本、延遲與安全測量。
- 影片對 prompt injection、憑證隔離、失控迴圈與觀測只輕觸，因此不能直接當生產部署指南。
- **適合對象：**第一次建立 Agent 的開發者、產品經理與自動化使用者。**是否值得看完整影片：值得**；純開發者可先看 `00:52–07:14`，再跳到 `17:44` 的全程式碼段落。

**可立即嘗試：**用你熟悉的語言做一個只有「搜尋」工具的迷你研究 Agent，限制最多 3 次工具呼叫，要求每個結論保留來源；記錄每輪的目標、工具、結果與停止原因，再比較一次性 prompt 是否已足夠。這會很快暴露出你真正需要的是 Agent，還是較簡單的固定工作流。

**候選排除說明：**本次也主動檢查中文與英文頻道。PAPAYA 電腦教室最新公開片約 9 天前，已超出一週範圍；另一支 2026-07-14、已破萬的中文候選沒有可取得的字幕／逐字稿，因此不猜測內容、不列入精選。

## 6. 今天值得嘗試

### 先做安全行動，再做一個 30 分鐘的 E3 小實驗

1. **若你使用 Hugging Face：**今天輪替 Access Token、移除不再使用的 Token，並檢查近期活動與自動化中的舊憑證。
2. 選一個小型程式修改，先寫下「預估只需讀哪些檔案、成功驗證是什麼」。
3. 只提供這些最小上下文給 Coding Agent；若測試失敗，再讓它多讀一層依賴。
4. 記錄 Token、讀取檔案數、耗時、返工次數與測試結果。不要只比較「感覺比較快」。
5. 若 repo 使用 Copilot Code Review，把 3–5 條真正可驗證的審查規則放進 `AGENTS.md` 或 review instructions，再用一個測試 PR 確認它是否遵守。
