### 3. Function Calling 的信心判斷，簡單單次方法可能比多次語意取樣更划算

- **Apple ML 上架：2026-07｜arXiv：2026-04-24｜性質：預印本／TMLR 審查中。**
- 《Uncertainty Quantification for LLM Function-Calling》專門研究工具呼叫是否能在執行前估計錯誤風險。作者發現，多次取樣的 Semantic Entropy 在 function calling 場景沒有明顯勝過簡單的單次取樣方法。
- 工具呼叫輸出有結構優勢：多次取樣時可依抽象語法樹聚類；單次方法則只計算函式名、參數值等有語意的 Token，減少格式 Token 干擾。
- 實務意義不是「找到通用信心分數」，而是先做 selective execution：低風險讀取可自動執行；付款、刪除、發送、改權限等不可逆動作，低信心或 schema 不一致時直接停下來要求確認。

來源：[Apple Machine Learning Research](https://machinelearning.apple.com/research/uncertainty-quantification-function-calling)、[arXiv 論文](https://arxiv.org/abs/2604.22985)

## 3. 新技術、新方法

### 用「路由與所有權」取代多 Agent 自由辯論

綜合論文與近期實務討論，較穩的多 Agent 設計是：

1. **一個 authoritative plan：**先明確定義目標、依賴與完成條件。
2. **一個 mutable surface 一位 owner：**同一檔案、模組或架構邊界同時只給一個 writer；研究與 review 可並行、寫入不可重疊。
3. **專家做路由依據，不做投票素材：**已知某 Agent 對某領域更可靠時，讓它擁有決策權或用外部測試評分，不要求所有 Agent 折衷。
4. **Reviewer 先保持唯讀：**writer 完成、測試與 diff 穩定後，再讓 reviewer 找證據與反例。
5. **單一 integration pass：**最後由一個人或整合 Agent 解決跨分支假設，重新跑完整驗證。

這是根據研究與社群經驗整理的工程推論，不是任何工具的保證行為。

### 在 Tool Calling 前加一個三層 gate

1. **語法 gate：**函式名、必要參數、型別、enum 與 schema 必須合法。
2. **語意 gate：**只用函式名與關鍵參數 Token 估信心；若多次取樣，先按 AST／參數結構聚類，不只比較自然語言相似度。
3. **影響 gate：**讀取、搜尋等低風險動作可自動執行；刪除、付款、發布、寄信與權限變更一律要求人確認，即使模型自稱高信心。

## 4. 社群實戰心得

### 多 Agent 真正有效的切法是「依賴與寫入權」，不是只分 coder／tester／reviewer

- 一個 2026-06-23 的 Reddit 討論在 2026-07-19 新增實作者回覆：可重複的流程是依 dependency 與 write ownership 分工；研究可自由 fan-out，實作要有明確檔案／任務所有權，reviewer 在 writer 完成前保持唯讀，最後只做一次整合。
- 其他回覆指出，worktree 在 checkout 成本低時很好用；若每份 checkout 都需要大型 build、服務或 seeded database，替代方案是 shared workspace 加 write lease，保證同一時間只有一位 writer。
- 這些是個人經驗，部分回覆帶自家工具揭露，且票數不高；可把它當 workflow hypothesis，不能當統計證據。它與論文「更多聲音可能稀釋專家」的結果方向一致，但兩者設定不同。

來源：[Reddit：實際多 Agent／平行 Claude Code workflow 討論](https://www.reddit.com/r/ClaudeCode/comments/1udrdgy/is_anyone_here_actually_using_multiagent_parallel/)

### 新手 AI Coding 的最大風險常不是模型，而是不知道 commit、branch、PR 代表什麼

- Gary Chen 新片的留言多數肯定用圖解釐清 Git 名詞；較有價值的問題集中在「兩個分支依賴的資料結構已分歧怎麼辦」與「AI 產生不用的程式碼如何清理」。這說明理解名詞只是第一步，介面相容性、測試與 dead-code review 仍需要工程判斷。

- **快速摘要：**影片用記帳 App 的例子，將 Git、GitHub、commit、push、clone、pull、branch、worktree、PR、merge、conflict、restore 與 revert 串成一條 Vibe Coding 安全流程。核心價值是讓非工程師聽懂 AI Coding Agent 在詢問什麼，但仍需自己決定何時存檔、如何隔離風險，以及衝突時產品邏輯要保留哪一邊。

**內容重點與時間點**

1. `00:00–01:02`：Claude Code／Cursor 常問的 commit、branch、PR 都指向版本管理與協作，不只是難背指令。
2. `01:02–03:21`：用「本地版本系統」和「雲端協作平台」區分 Git 與 GitHub；示範 `git init` 的角色。
3. `03:21–06:11`：commit 是本地檢查點，push 才把 commit 送到 remote；push 前先檢查 `.env`、API key、密碼和 `.gitignore`。
4. `06:11–10:42`：clone 取得完整 repo，pull 同步 remote；branch 將大改動隔離，不直接在 main 上實驗。
5. `10:42–15:53`：worktree 讓多個 branch 有各自工作目錄，適合平行 Agent；PR 用於提出、檢視與測試變更，再 merge 回 main。
6. `15:53–19:15`：未 commit 的錯誤可視情況用 restore；已 commit 的錯誤通常用 revert 新增反向 commit，保留可追蹤歷史。

**影片示範的工作流程**

1. 建立 repo 前先確認哪些檔案絕不能追蹤，設定 `.gitignore`，並用 secret scanning 或人工檢查補強。
2. 完成一小段、已能執行且測試通過的功能後再 commit，訊息要寫清楚做了什麼。
3. 需要分享或備份才 push；讓他人協作時，從最新 main 建 branch。
4. 多 Agent 平行實作時，每個 Agent 使用獨立 branch／worktree，並分配不重疊的寫入範圍。
5. PR 中檢查 diff、測試與衝突；合併後，本機 main 要再 pull，下一個 branch 才不會從舊狀態出發。
6. 發現錯誤時先看 `git status`、`git diff` 與 log，再決定 restore、revert 或修正 commit，不要只下「全部還原」這種模糊指令。

**涉及工具／功能**

- Git、GitHub、Claude Code、Cursor、VS Code。
- commit、remote／origin、push、clone、pull、branch、worktree、pull request、merge、conflict、restore、revert、`.gitignore`。

**作者心得、優缺點與限制**

- 作者主張 Vibe Coder 不必先成為 Git 專家，但必須理解每個動作是在存檔、同步、隔離、審查還是復原，才能對 Agent 下產品與風險決策。
- 優點是例子連貫、名詞關係清楚，也把 secret 不可上傳、worktree 隔離與合併後 pull 等常見踩雷放進同一流程。
- **第一個過度簡化：**影片說不能像 Google Drive 一樣把資料夾拖到 GitHub；GitHub 官方其實允許瀏覽器拖放檔案或資料夾，最多 100 個檔案、每檔 25 MiB。只是正式開發仍應用 Git，因為 web upload 會直接產生 commit，也不套用本機 `.gitattributes` 流程。
- **第二個過度簡化：**commit 不是「絕對安全且永久」的保險；歷史可被 amend、rebase、reset 或 force-push 改寫。restore 也可能丟掉未 commit 內容，必須先看 diff、指定 path，必要時先備份。

## 6. 今天值得嘗試

### 為下一個 Agent 任務加上「一位 writer、三個 gate」

1. 在任務開頭寫清楚唯一 writer，以及它可修改的檔案／模組；其他 Agent 只做研究或 review。
2. 要求 writer 從最新基準建立 branch／worktree，先回報 `git status` 與驗證命令。
3. 每次工具呼叫先過 schema gate；涉及刪除、發布、付款、寄送或權限時，再加人工確認 gate。
4. 完成後由 reviewer 對照需求、diff 與測試找反例，不參與同一輪寫入。
5. 最後只做一次 integration pass，重新跑完整測試；若結果不一致，回到 owner 修正，不用多人投票平均答案。
