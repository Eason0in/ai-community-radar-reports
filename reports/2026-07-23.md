## 1. 今日最重要的 5 件事

### 1. OpenAI 推出 Presence，把客服 Agent 做成受控的企業產品

**發布日期：2026-07-22｜類型：官方產品公告**

OpenAI 發布 [Presence](https://openai.com/index/introducing-openai-presence/)，定位為可部署於語音與文字客服的企業級 Agent：除了回答問題，也能依工作範圍存取公司系統、執行獲准動作，並在必要時轉交真人。產品把 SOP、權限、核准流程、交接、模擬測試、評測與 Codex 輔助改善整合在同一套治理框架內。

- OpenAI 表示，其英文客服目前有 75% 的來訊可不經真人解決，且十天內人工轉接率下降 15 個百分點；這是 **OpenAI 自家場景與廠商公布結果**，不是獨立評測。
- BBVA、SoftBank、IAG 正在探索或測試，但不代表已全面上線。
- 目前只向符合資格的企業客戶有限度開放，須由 OpenAI Forward Deployed Engineers 或指定整合商協助部署，並非自助式 SaaS。
- 真正值得注意的不是「又一個客服機器人」，而是 OpenAI 把 Agent 的權限、政策、評測與持續改善做成可交付的營運層。

### 2. AMD 與 Anthropic 簽下最高 2GW 的 AI 基礎設施合作

**發布日期：2026-07-22｜類型：官方產業公告**

[AMD 與 Anthropic 宣布策略合作](https://ir.amd.com/news-events/press-releases/detail/1292/amd-and-anthropic-announce-strategic-partnership-to-deploy-up-to-2-gigawatts-of-amd-instinct-mi450-series-gpus)，規劃部署最高 2GW 的 AMD Instinct MI450 系列 GPU；首個 1GW 預計於 **2027 年上半年**啟用。系統將採用 AMD Helios 機架架構，包含 MI455X、EPYC「Venice」、Pensando 網路與 ROCm。

- Anthropic 已使用 MI355X，雙方還會以 Claude 協助最佳化 Instinct 工作負載與 ROCm 開發。
- AMD 同時承諾未來最高 50 億美元的 Anthropic 策略性股權投資。
- 這是「供應商、客戶、軟體協作與投資」綁在一起的多年合作；不能把 2GW 解讀成已交付算力。
- 對市場的意義是 Anthropic 進一步分散加速器供應，而 AMD 取得一個大型前沿模型客戶來驗證軟硬體堆疊。

### 3. Upstage 發布 Solar Open 2：250B MoE、1M context 的開放權重模型

**發布日期：2026-07-22｜類型：官方模型發布**

Upstage 發布 [Solar Open 2](https://www.upstage.ai/blog/en/solar-open-2) 並在 [Hugging Face](https://huggingface.co/upstage/Solar-Open2-250B) 提供權重。模型總參數 250B、每次啟用 15B，支援最長 100 萬 token，主打韓文、英文與日文，以及 Agent 與工具使用。

- 採自訂 Upstage Solar License，可商用、微調、建立衍生模型與蒸餾；較精確的稱呼是 **開放權重**，不宜只因可下載就等同於傳統開源授權。
- 官方建議 BF16 至少使用 4 張 H200；量化後仍建議 2 張 H200，個人本機使用門檻很高。
- 可接入 Claude Code 與 Hermes Agent；官方 Playground 開放至 2026-07-31。
- 官方 benchmark 顯示多項語言與 Agent 能力表現具競爭力，但目前仍是 **廠商結果**，尚缺獨立重測與真實長上下文壓力測試。

### 4. NVIDIA 開源醫療物理模擬模組，讓手術機器人先在 GPU 世界練習

**發布日期：2026-07-22｜類型：官方技術發布／研究成果**

NVIDIA 發布 [Isaac for Healthcare 的開源 Medical Physics Simulation 模組](https://blogs.nvidia.com/blog/medical-physics-simulation-open-source/)，用 GPU 模擬解剖組織、導管與醫療器材互動，讓機器人政策能在實體硬體與臨床環境之前進行訓練與測試。[技術文件](https://isaac-for-healthcare.github.io/medical-physics-simulation/)涵蓋 CUDA、Warp、Newton、Cosmos 等元件。

- 官方案例包含血管、導管、X 光成像與強化學習，並可用 Cosmos-H Dreams 產生視覺資料。
- NVIDIA 引述相關研究，稱 8,192 個平行環境可把訓練由五小時以上縮短到兩分鐘內；這是特定模擬設定的結果，不代表臨床有效性或安全性已獲驗證。
- 對醫療 AI 團隊而言，價值在於可重現稀有或高風險情境；但 simulation-to-real 落差、組織模型精度、法規與真實臨床驗證仍是關鍵限制。

### 5. GitHub Copilot 新增 Impact Dashboard，但「相關」不等於「因果」

**發布日期：2026-07-22｜類型：官方產品更新**

GitHub 為 Enterprise 管理員與組織擁有者推出 [Copilot usage metrics impact dashboard](https://github.blog/changelog/2026-07-22-new-copilot-usage-metrics-impact-dashboard/)。它依最近 28 天使用行為，把開發者分為 code-first、agent-first、multi-agent／Copilot app 與 passive cohorts，再比較 PR 合併量、合併速度、每日程式碼行數、採用率等六個月趨勢。

- 優點是企業終於能把不同 AI 使用型態與交付指標放在同一個畫面觀察。
- 主要風險是選擇偏差：本來就高產出的團隊可能更積極採用 Agent。Dashboard 能顯示關聯，不能單獨證明 Copilot 導致產能提升。
- 實務上應再搭配品質、回滾、事故、review 負擔與開發者滿意度，避免只追求 LOC 或 PR 數。

## 3. 新技術、新方法

### AutoIndex：讓 Agent 改寫「索引策略」，而不只調檢索參數

**發布日期：2026-07-21｜類型：研究預印本／開源實作**

[AutoIndex 論文](https://arxiv.org/abs/2607.18603)把文件進入搜尋索引前的轉換寫成可執行的 representation program，例如切分、補充、正規化、重新加權與重組。Agent 先分析檢索失敗，再產生候選程式，經驗證集選出較佳策略；部署後的索引流程本身不必每次呼叫 LLM。[程式碼已公開](https://github.com/auto-index/autoindex)。

- 作者在 CRUMB 的八個任務上，以固定 BM25 為底座，報告平均 Recall@100 增加 8.4%、nDCG@10 增加 8.3%，最佳任務分別增加 30.5% 與 43.6%。
- 方法的亮點是把最佳化空間從「換 embedding／調 top-k」移到資料表示本身。
- 風險是 Agent 可能對小型驗證集過度擬合；研究仍是作者自行評測的預印本，還需要其他語料、向量檢索與線上系統重現。

### AgentDebugX：把多 Agent 除錯做成 Detect → Attribute → Recover → Rerun

**發布日期：2026-07-21｜類型：研究預印本**

[AgentDebugX](https://arxiv.org/abs/2607.18754)提出四階段閉環：偵測異常、定位是哪個 Agent／哪一步、提出修復，最後重新執行驗證。它也建立 DeepDebug 多輪診斷資料與 Who and When attribution benchmark。

- 論文報告 Qwen3.5-9B 的 agent-and-step 精確率為 28.8%，高於最強單次判斷基線的 21.7%。
- 在 73 個失敗的 GAIA 任務中，單次重跑修復 13 個；基線為 4–6 個，整體成功率由 55.8% 提升到 63.6%。
- 結果支持「先歸因、再修復、一定重跑」的工作流，但 28.8% 的精確定位也顯示離可靠自動除錯仍很遠。

## 4. 社群實戰心得

### 生產環境修復不能只靠 Agent 自評：Cleric 的四週回看

**發布日期：2026-07-22｜類型：廠商工程實戰，自家資料**

AI SRE 廠商 Cleric 在 [How we verify Cleric’s production fixes](https://cleric.ai/blog/verifying-fixes) 分享四週真實告警的回看：有些被判定「已修好」的問題後來重複發生，常見原因是只做了暫時緩解，或驗證器把「程式已進 main」誤認為「已部署並生效」。

- 將修復後是否再次出現同類告警，視為比 Agent 自我評分更硬的成功條件。
- 用獨立 verifier 讀取新證據，而不是讓原 Agent 評自己的答案。
- 便宜且確定性的檢查，例如部署狀態、版本、告警與重跑結果，應優先於語言模型判斷。
- Cleric 表示，在同一批 60 次調查中，獨立、具證據依據的審核比 Agent 自評更能預測結果；但文章未提供足以獨立重算的完整樣本與統計，因此應視為 **廠商經驗**。

**可移植的做法：** 對 coding Agent 的 PR，不要把「測試寫了」「分支合併了」當完成；先定義可觀察結果，再由不同 context 的 reviewer 檢查，最後在實際環境重跑。

## 5. YouTube 深度整理

### Gary Chen｜17 萬星的 Matt Pocock skills，到底強在哪？skills 全拆解

**發布日期：2026-07-22｜查核時觀看次數：15,803｜長度：20:01｜字幕：繁體中文字幕已完整查閱**

[觀看影片](https://www.youtube.com/watch?v=aR97E7aKEgg)｜頻道：Gary Chen

**快速摘要：** 影片拆解 Matt Pocock 的 skills 工作流：先用逐題追問收斂需求，再寫規格、依使用者可見的垂直切片拆票，以 TDD 實作，最後用獨立 review 與架構檢查收尾。內容的實用點在於把「讓 Agent 寫 code」改成一連串可驗證的小決策；但影片沒有用同一任務做對照 benchmark，對 Superpowers 與模型能力的比較屬作者觀點。

**內容重點與時間點：**

- **00:00–02:21**：主張 skill 應小而可組合，用明確流程降低模型輸出的隨機性。
- **02:22–04:44**：grill-me 每次問一題、附建議答案；未達成共識前不開始寫 code。to-spec 把共識寫成規格，但避免先塞進實作細節。
- **04:45–06:25**：to-tickets 以使用者可見的垂直切片拆工作，不以 database／backend／frontend 水平分層，讓每張票都能單獨驗證。
- **06:26–10:05**：implement 採 red-green TDD；完成後另開 review context，檢查規格、標準與 Shotgun Surgery、Feature Envy、Data Clumps 等 code smells。
- **10:06–15:25**：說明如何寫好 skill，以及用 improve-codebase-architecture 找出 shallow module、刪除測試與高槓桿重構機會。
- **15:26–18:39**：grill-with-docs 會保留術語、決策與流程文件；作者認為模組化 skills 比固定九步流程更適合當前強模型。後半句沒有實驗支持，應視為個人判斷。

**建議工作流程：**

1. 對需求一次只問一個決策問題，並附預設建議。
2. 把共識整理成規格，不提前鎖死實作。
3. 以可見行為拆成能獨立交付的垂直切片。
4. 每個切片先寫會失敗的測試，再寫最小實作使其通過。
5. 以新 context 或不同 reviewer 對照規格與工程標準。
6. 定期跑架構檢查，但只處理可證明有收益的重構。

**涉及工具／功能：** Matt Pocock skills、Codex／Claude Code 類 coding agents、TDD、spec、tickets、code review、architecture review。官方 [mattpocock/skills repository](https://github.com/mattpocock/skills) 確認其目前提供 grill-with-docs → to-spec → to-tickets → implement 的組合流程，以及 TDD、review 與架構 skill；影片所說「模組化一定比 Superpowers 好」不是該 repo 證實的事實。

**作者心得：** 作者偏好能按需求自由組合的小型 skills，認為領域專業與完成條件比一味堆疊固定流程更重要。

**優點：**

- 把 repo 中多個 skill 的角色、先後關係與使用時機講得清楚。
- 垂直切片、失敗測試、獨立 review 都能直接移植到日常 Agent workflow。
- 有指出 skill 需要刪減冗詞、加入觸發詞與明確完成條件。

**缺點與限制：**

- 沒有同一任務的速度、品質或成本對照，不能據此判定哪套流程優勝。
- 「AI 會作弊」等表述較絕對；真正問題是如果測試與驗證目標不完整，Agent 容易最佳化錯誤指標。
- 影片約 **16:27** 起推廣作者自己的 Patreon 文章；未見第三方贊助揭露，屬自我推廣。

**適合對象：** 已經用 Codex、Claude Code 或其他 coding Agent 寫功能，卻常遇到需求沒問清楚、一次改太多、測試與 review 流於形式的開發者。

**是否值得看完整影片：** 值得。時間有限可優先看 02:22–10:05 的需求、拆票、TDD 與 review 段落；比較不同 workflow 的結論則保留判斷。

**可立即嘗試：** 選一個低風險功能，只做一條垂直切片：先讓 Agent 每次問一題、寫出驗收規格，接著建立一個必定失敗的測試，完成最小修正後，再用新的 context 只檢查「是否真的滿足規格」。

> 其他候選查核：PAPAYA 電腦教室近一週沒有找到符合本期條件的新片；Tech With Tim 於 2026-07-22 發布的 Hermes Agent 課程查核時僅 1,468 次觀看，未達門檻；Matthew Berman 的 2026-07-22 影片雖超過 1 萬次觀看，但屬昨日已報事件的評論型延伸，且標題與內容偏事件敘事，因此不納入。

## 6. 今天值得嘗試

### 為一個 Agent 任務補上「獨立驗證閉環」

花 30 分鐘，挑一個昨天已由 Agent 完成的小修改：

1. 寫下一句可觀察的完成條件，例如「部署版本 X 後，同一輸入不再產生錯誤 Y」。
2. 讓新的 Agent context 只讀規格、diff、測試與部署證據，不讀原 Agent 的自評。
3. 先跑確定性的檢查，再讓 reviewer 解釋殘餘風險。
4. 若失敗，記錄是哪一步、哪個假設錯誤，以及修復後的重跑結果。

這同時吸收今天三個訊號：Gary Chen 影片的獨立 review、AgentDebugX 的歸因後重跑，以及 Cleric 對生產環境結果的驗證。重點不是增加流程數量，而是把「完成」改成能被外部證據推翻或確認的狀態。
