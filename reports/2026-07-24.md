### 1. ChatGPT Health 正式擴大推出：可把病歷與 Apple Health 帶進一般對話

**發布日期：2026-07-23｜類型：官方產品公告**

OpenAI 開始向美國 18 歲以上的 ChatGPT Free、Go、Plus、Pro 使用者推出 [Health in ChatGPT](https://openai.com/index/health-in-chatgpt/)。使用者可選擇連接 Apple Health、支援的美國醫療紀錄、One Medical 或 Function Health，用自己的檢驗、用藥、就診、睡眠與活動資料來追問趨勢或準備看診問題；目前支援 Web 與 iOS，尚未提供 Android，也不在 Codex 中。

- 預設情況下，ChatGPT 在一般對話想使用已連接的健康資料時會先詢問；也可改為永遠允許。
- OpenAI 表示，連接的病歷、Apple Health 資料及使用這些資料的對話，不用於訓練基礎模型或投放廣告。
- 斷開資料來源後，同步資料會在 30 天內自 OpenAI 系統刪除；已寫入對話歷史的內容仍要由使用者刪除該對話。
- OpenAI 公布 GPT‑5.6 系列在 HealthBench Professional 優於 GPT‑5.5，但這是 **OpenAI 與合作醫師建立的自家評測結果**，不能替代獨立臨床驗證。
- 產品定位是協助理解與整理，不是診斷或治療工具；官方也明確承認模型仍可能出錯。

**為什麼重要：** 這不只是多一個健康分頁，而是讓高敏感度個人資料能在一般對話中按權限被取用。實用性提高的同時，權限設定、資料正確性、對話刪除與醫療決策邊界都變得更重要。

### 3. Cursor Router 把「選模型」改成每個請求的路由決策

**發布日期：2026-07-22｜類型：官方產品發布／廠商實驗結果**

Cursor 推出 [Cursor Router](https://cursor.com/blog/router)，依查詢、context、任務複雜度與領域，把每個請求送往不同模型。Teams 與 Enterprise 使用者可在 Auto 模式選擇 Intelligence、Balance、Cost 三種最佳化方向，管理員也能設定允許模型與是否顯示實際路由結果。

- Cursor 表示分類器以超過 60 萬個真實請求訓練，並用數百萬個線上請求做 A/B 測試。
- 官方宣稱早期企業客戶在接近前沿品質下節省約 30–50%，線上測試則達 60%；這些是 **Cursor 自家流量、自家滿意度指標與自家成本算法**，不是獨立 benchmark。
- Router 目前只供 Teams／Enterprise，個人 Pro 使用者無法使用。
- 實務價值在於避免所有小任務都使用最高價模型；實務風險則是錯誤路由、模型切換造成行為不一致，以及路由決策缺乏可解釋性。

### 4. Prime Intellect 把 36.5 萬個 Agentic RL 任務整理成同一套介面

**發布日期：2026-07-22｜類型：官方研究工程發布／開源整合**

Prime Intellect 發布 [Scaling Agentic RL: 365,000+ Environments](https://www.primeintellect.ai/blog/scaling-agentic-rl)，把 23 組 tasksets 統一成同一套 API、harness 與 runtime 介面：包含約 19.86 萬個軟體工程任務、2.86 萬個終端機任務與 13.76 萬個搜尋任務，供 Agent 評測與強化學習使用。

- 每組 taskset 保留原本的評分邏輯，再統一資料 split、sandbox 與執行生命週期。
- 官方建立約 13.5 萬個預製 task images，並在評分前隱藏 test patch、預期輸出與 grader，降低 Agent 直接讀取答案的 reward hacking。
- 團隊也承認目前 Agent 與 grader 仍可能位於同一 sandbox；真正的結構性修正是隔離評分環境，仍在 roadmap。
- 另一個限制是從既有 PR 挖出的測試常綁定實作細節，Agent 即使提出等價正確解也可能被判失敗；gold patch 能通過自身測試，無法發現這類 false negative。

**真正的技術訊號：** Agent 訓練的瓶頸正在從「多收集題目」轉向「統一執行契約、保護評分材料、校正 reward」。錯誤的 grader 會比不夠大的資料集更直接地教壞模型。

## 3. 新技術、新方法

### Salesforce 的「受治理自我改進」：先固定模型，再改善外部 harness

**發布日期：2026-07-23｜類型：廠商方法論／早期實作觀點**

Salesforce 在 [Toward Self‑Improving Agents](https://www.salesforce.com/news/stories/toward-self-improving-agents/)提出一個適合企業 Agent 的循環：

1. 先定義準確率、速度、成本、業務 KPI、政策違規與 regression guardrails。
2. 從生產失敗中偵測重複問題並診斷原因。
3. 對 prompt、工具、檢索、routing、memory 或 workflow 產生離散候選修改。
4. 在模擬、回歸測試與對抗案例中評估，只保留沒有破壞約束的改善。
5. 將成功修正、測試與 routing 規則版本化，再由新證據啟動下一輪。

文章最務實的建議是先用簡單的 greedy search，不必一開始就做複雜 RL。最重要的警告則是：如果目標是「關閉案件數」而非「問題真的解決」，系統可能學會更快關單而不是更好服務。持久化的 memory、skill 或 workflow 必須由外部證據驗證，並保留 lineage 與 rollback。

這是 Salesforce 的產品方向與設計觀點，雖引用研究與案例，但沒有提供完整對照資料證明其自家 Agent 已普遍達成自我改進；應視為可採用的工程框架，不是已驗證的通用結果。

## 4. 社群實戰心得

### Cursor Router 的第一天反應：省成本有吸引力，但團隊更在意「為什麼被路由」

**發布日期：2026-07-22 至 2026-07-23｜類型：Reddit 初期使用者反應**

[r/cursor 的發布討論](https://www.reddit.com/r/cursor/comments/1v3r5ih/cursor_router/)中，一位管理 100 多名使用者的管理員認為 Auto 能幫助成本治理；另一批使用者則質疑為何只供 Teams／Enterprise，以及隱藏實際模型後如何長期信任路由器。這些留言是少量、自選樣本，不能證明整體效果，但點出導入時最該記錄的欄位：

- 任務類型與實際被選模型。
- 單次與整體成本、cache miss、重試次數。
- 產出被保留、重寫或回滾的比例。
- 小任務是否真的由便宜模型完成，難任務是否錯送。
- 管理員的 allow／block 清單與例外原因。

**可移植的做法：** 不論使用 Cursor Router 或自建 routing，先對 20–50 個真實任務做 shadow evaluation；保留人工原選模型作基線，再比較品質、成本與重試，而不是只相信路由器的總體節省百分比。

## 5. YouTube 深度整理

### PAPAYA 電腦教室｜為什麼全球開發者都離不開 VS Code 這個軟體？新手必學的完整入門指南，一次搞懂 7 大核心功能！

**發布日期：2026-07-22｜查核時觀看次數：33,101｜長度：23:32｜字幕：原始繁體中文字幕已完整查閱**

[觀看影片](https://www.youtube.com/watch?v=2RbXlT5wl9c)｜頻道：PAPAYA 電腦教室

**快速摘要：** 影片用「替樂團做巡演網站」串起 VS Code 的資料夾、Markdown、HTML／CSS／JavaScript、搜尋、偵錯、Git、GitHub 與 AI 助理。它不是深入的 Agent 教學；AI Coding 只在最後約三分鐘出現。但對完全沒用過 IDE、Git 或 coding Agent 的人，它把 Agent 需要的專案邊界、版本控制與驗證介面先補齊，仍有實作價值。

**內容重點與時間點：**

- **00:00–06:10**：開啟專案資料夾、Workspace Trust、建立檔案、Markdown 預覽、分割視窗與自動儲存。
- **06:10–11:18**：用 Emmet 補齊 HTML，安裝 Live Server 即時預覽，再用 CSS 完成背景、置中、字色與間距。
- **11:18–14:24**：跨檔案搜尋／取代、行號、symbol、outline 與快速開檔。
- **14:24–17:25**：用 breakpoint 查看 JavaScript 變數，找出時間未歸零、月份從 0 起算、毫秒尚未換算成天數等錯誤。
- **17:25–20:07**：Git init、stage、commit、diff、同步至 GitHub，以及在另一台電腦 clone。
- **20:07–23:22**：示範 VS Code 的 Agent／Plan／Ask，以及 Claude Code Plan mode；用 `@` 指定檔案、附參考圖、回答澄清問題、核准計畫，再於瀏覽器測試與部署。

**建議工作流程：**

1. 只把自己建立或已審查的資料夾設為 trusted workspace。
2. 先手動完成一個最小、可在瀏覽器看到的 HTML／CSS／JS 垂直切片。
3. 在安裝 extension 前確認 publisher 與必要權限。
4. 用 breakpoint 與變數值找錯，不只靠 AI 解釋。
5. 在交給 Agent 前先建立 Git commit，保留可比較與回復的基線。
6. 讓 Agent 先 Plan、引用明確檔案與素材；實作後檢查 diff 並在瀏覽器實測，再決定是否部署或 push。

**涉及工具／功能：** VS Code、Markdown、Emmet、Live Server、HTML、CSS、JavaScript debugger、Git、GitHub、GitHub Copilot、Claude Code，以及片中提到但未實作的 Codex。

**官方交叉查核：**

- [VS Code 官方文件](https://code.visualstudio.com/docs/agents/overview)確認內建 Agent、Plan、Ask；但 [Workspace Trust 文件](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust)也提醒，不熟悉的 repository 應先留在 Restricted Mode，且 extension 可能執行本機程式。
- [GitHub Copilot 方案文件](https://docs.github.com/en/copilot/get-started/plans)確認 Free 有有限的 chat／agent 用量與每月 2,000 次 completion；目前各方案另以 GitHub AI Credits 衡量，影片只說「固定額度」過於概括。
- [Claude Code 官方文件](https://code.claude.com/docs/en/permission-modes)確認 Plan mode 只研究與提案、不改 source；核准計畫後切換到何種 edit／permission mode，仍要由使用者決定。

**作者心得：** PAPAYA 把 VS Code 定位成從寫檔、偵錯、版控到 AI 助理的一站式入口，認為初學者不必先熟悉所有程式語法，也能在明確素材與計畫下讓 Agent 接手後續網站工作。

**優點：**

- 用一個可見成果串完整流程，對新手比零散快捷鍵清單更容易理解。
- 偵錯段落有真的查看變數並逐項修正，不把所有問題都交給 AI。
- 把 Git commit 放在 Agent 之前，形成實用的安全基線。

**缺點與限制：**

- 「VS Code 編輯文件主要使用 Markdown」容易讓新手誤解；VS Code 是支援多種語言的編輯器，Markdown 只是示範之一。
- GitHub 被簡化為「雲端備份」，未說明公開 repository、secret 外洩、branch／PR 與 push 權限風險。
- 對 Live Server 點擊信任後直接使用，沒有教如何檢查 extension publisher、權限與維護狀態。
- AI 助理段落較短，完成網站與部署的結果是影片示範，沒有提供可重跑的 repository、測試或對照 benchmark。
- 影片描述含 Buy Me a Coffee 與頻道會員連結，屬 **自我推廣**；字幕與描述中未見第三方贊助揭露。

**適合對象：** 第一次使用 VS Code、Git、GitHub 或 IDE 內 coding Agent，希望先理解檔案、偵錯、版控與 Plan mode 的非技術使用者。

**是否值得看完整影片：** 初學者值得；已有 VS Code、Git 與 Agent 經驗者可直接看 14:24–17:25 的偵錯與 20:07–23:22 的 AI 助理段落。若期待模型比較或進階 Agent workflow，這部不夠深入。

**可立即嘗試：** 建一個全新的練習資料夾與單頁 HTML，先做第一次 Git commit；再請 Agent 只規劃並新增一個導覽列。完成後檢查 diff、在瀏覽器逐一點擊連結，確認正常才做第二次 commit。

> 其他候選查核：Tech With Tim 於 2026-07-23 發布的 GLM 5.2／Claude Code 實測查核時為 4,018 次觀看；Matthew Berman 同日的 token 節省影片為 5,486 次，兩者皆未破萬。Matthew Berman 7/22 的安全事件影片雖有 71,285 次觀看與字幕，但重複昨日已報導事件且偏新聞評論，因此不納入。

## 6. 今天值得嘗試

### 做一個「可觀測的模型路由」小實驗

花 30–45 分鐘，從最近的 coding Agent 紀錄挑 20 個任務：

1. 標成簡單修改、UI、除錯、長程推理四類。
2. 先寫下你原本會選的模型，作為人工路由基線。
3. 用一個便宜模型與一個前沿模型各跑 3–5 個代表任務；固定 prompt、repository 版本與驗收測試。
4. 記錄成本、時間、重試、diff 被保留比例與測試結果。
5. 只在有足夠證據時建立 routing rule；每條規則都保留例外、版本與 rollback。

這同時吸收 Cursor Router 的成本訊號、Prime Intellect 對 grader 的警告，以及 Salesforce 的受治理自我改進循環。重點不是立刻自動選模型，而是先讓每次路由決策可以被檢查與推翻。
