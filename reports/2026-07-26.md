## 1. 今日最重要的 3 件事

### 1. AMD 把 AI 基礎設施從單顆 GPU 拉到完整 rack：Helios、MI455X 與開放互連

**發布日期：2026-07-23｜類型：官方硬體發布／廠商規格**

AMD 在 [Advancing AI 2026](https://www.amd.com/en/corporate/events/advancing-ai.html)公布 Helios rackscale reference design。單 rack 整合 72 顆 MI455X、EPYC 9006「Venice」CPU 與 Pensando 網路，採 OCP Open Rack Wide、UALink／UALoE 與 Ultra Ethernet 等標準；[Helios 規格頁](https://www.amd.com/en/products/rackscale-solutions/helios.html)列出 31 TB HBM4、2.9 EFLOPS FP4、1.4 EFLOPS FP8 與 260 TB/s aggregate scale-up bandwidth。

[MI455X](https://www.amd.com/en/products/accelerators/instinct/mi400.html)單卡提供 432 GB HBM4 與 23.3 TB/s peak theoretical memory bandwidth。AMD 宣稱其 FP4 峰值、記憶體容量與頻寬優於 NVIDIA Vera Rubin；這些是 **AMD 依理論峰值與自選比較口徑公布的廠商結果**，不是獨立 workload benchmark。實際訓練／推論效益仍取決於 ROCm kernel、collective、拓撲、功耗、供貨與模型能否有效吃滿整個 rack。

**為什麼重要：** frontier AI 的競爭單位已從「一張卡」轉成 compute、HBM、scale-up／scale-out network、CPU orchestration、power、cooling 與軟體共同設計的 rack。採購時應比較可重現的 end-to-end tokens／秒、tokens／瓦、失敗恢復與有效利用率，而不是只看峰值 FLOPS。

### 2. ROCm.ai 用 Skills、CLI、Console 與 Hyperloom 把 AMD 部署流程 Agent 化

**發布日期：2026-07-23｜類型：官方開發工具／Tech Preview**

[ROCm.ai](https://www.amd.com/en/blogs/2026/rocm-ai-the-ai-native-developer-experience-for-building.html)試圖把 AMD 最常見的「安裝、版本、診斷、serve、效能調校」摩擦收斂成四層：

- **AMD Skills**：把 AMD 驗證過的 ROCm 流程交給 Codex、Claude、Cursor 等 coding agents；現有例子包含 Instinct 上用 vLLM serving、PyTorch trace 分析、local AI routing。
- **ROCm CLI**：提供 deterministic、可放進 CI 的 `rocm install`、`rocm doctor`、`rocm serve`、`rocm update` 執行層。
- **ROCm Console**：集中 workload state、telemetry、logs 與 diagnostics，讓 Agent 的建議有可觀測資料。
- **ROCm Hyperloom**：以 profiling→瓶頸定位→修改→benchmark→correctness validation 的迴圈調整 host code 與 GPU kernels。

目前 AMD Skills catalog 明確標為 **Tech Preview**；部分 ROCm Doctor、HIP replay、kernel optimizer 與 APU memory tuner 仍是 coming soon。官方也尚未提供足以判斷 Hyperloom 平均加速幅度、失敗率或跨模型泛化能力的獨立結果。

**真正值得採用的設計：** Agent 負責提出與執行候選操作，CLI 保持 deterministic，Console 留下證據，最後以 correctness gate 決定是否保留最佳化。這比讓聊天模型直接自由修改驅動、kernel 與環境變數更可稽核。

### 3. Laguna S 2.1：118B MoE、每 token 啟用 8B，並公開最終評測 trajectories

**發布日期：2026-07-21｜類型：官方模型發布／廠商評測**

Poolside 發布 [Laguna S 2.1](https://poolside.ai/blog/introducing-laguna-s-2-1)：118B total／8B active 的 MoE coding model，支援 thinking 與 no-thinking 下最高 1M context；提供 BF16、FP8、INT4、NVFP4、GGUF、MLX 與 DFlash draft model，採 OpenMDW-1.1 license，可在 Hugging Face 取得。

- Poolside 自報 Terminal-Bench 2.1 為 70.2%、SWE-Bench Multilingual 78.5%、SWE-Bench Pro public 59.4%、DeepSWE 40.4%。
- Max thinking 把 Terminal-Bench 2.1 從 60.4% 拉到 70.2%，DeepSWE 從 16.5% 拉到 40.4%，但會增加 completion tokens；目前只有 off／max，沒有 low／medium／high。
- 官方同時揭露限制：第三方 harness 的 tool schema 稍有差異時可能沿用記憶中的格式、nested JSON tool arguments 可能 escape 錯誤，並可能長時間 overthink。
- 最有價值的不是單一榜分，而是官方開放[最終評測完整 trajectories](https://trajectories.poolside.ai/)，讓外界檢查 prompt、工具呼叫、重試與 reward hacking。

**可信度界線：** Poolside 明說跨模型比較會混用 vendor、leaderboard 與第三方的最大分數，DeepSWE 也用了不同 harness，因此不能視為嚴格同條件排名。它至少把不可比性、完整 trajectory 與自家 harness 講清楚，透明度高於只公布一張 leaderboard 圖。

## 2. 新模型與產品更新

### AMD 與 Cerebras 拆分 prompt processing 與 decode

**發布日期：2026-07-23｜類型：官方合作公告／前瞻效能模型**

[AMD–Cerebras 聯合方案](https://newsroom.amd.com/news/aai-2026-cerebras-inference/)把 AMD Helios 當高吞吐 prompt／long-context engine，Cerebras Wafer-Scale Engine 負責 memory-bandwidth-sensitive 的 decode／token generation。首波預計 2026 下半年經 Cerebras Cloud 提供。

雙方宣稱在 Kimi 2.6 1T model、相近 interactivity point 下，相較 Cerebras WSE-only 可達最高 5 倍 tokens／秒／瓦；這是 **2026 年 7 月由 AMD Performance Labs 與 Cerebras 建模的結果**，產品尚未普遍可用，也不是客戶 production measurement。

這個架構的重要性在於：prefill 與 decode 的硬體最佳點不同。若能把 routing、KV transfer、batching 與 failure recovery 做好，異質 compute 可分別最佳化 throughput 與 latency；但跨引擎資料搬移、tail latency、成本與 operational complexity 仍需上線數據驗證。

### Unsloth 正式擴大 AMD／ROCm 支援

**發布日期：2026-07-20｜類型：官方開源工具更新**

[Unsloth for AMD](https://unsloth.ai/docs/basics/amd)把 local inference、fine-tuning、RL 與 deployment 延伸到 Radeon RX 7000／9000、Instinct MI300／MI350、Strix Halo／Ryzen AI Max 等 AMD 平台。其 [GitHub releases](https://github.com/unslothai/unsloth/releases)也可看到 ROCm installer／hardware detection、ROCm test suite、bitsandbytes 4-bit decode 與相關修正。

但「支援 AMD」不等於任意 AMD 卡、OS 與模型組合都同等成熟。官方細部 guide 仍要求先核對 ROCm／PyTorch wheel、GPU architecture 與 framework 相容性；使用前應先建立獨立環境，跑小模型 smoke test，再做 full fine-tune。

## 3. 新技術、新方法

### 把 Agent 最佳化流程做成「可回退的實驗迴圈」

**發布日期：2026-07-21 至 2026-07-23｜類型：官方案例綜合／工程方法**

ROCm Hyperloom 與 Laguna S 2.1 的 harness optimization 案例呈現相同模式：

1. 先建立可重現 baseline 與 correctness tests。
2. Agent 一次只改一種方法。
3. 每次修改都跑 benchmark，不靠主觀「看起來更好」。
4. 只有 measurably wins 的版本才保留，否則回退。
5. 當 wall-clock 難以分辨時，換成 memory allocation 等更穩定的 proxy。
6. 最後再用 race detector、static checks 或 production-like test gate 驗證。

Poolside 表示其內部案例經多輪嘗試後把 harness wall-clock 改善 5.2%、allocation 降約 70%，並用 Go race detector 與 `go vet` gate；仍屬廠商自家 repository／環境結果。可移植的重點不是 5.2%，而是 **Agent 必須被測量函數、一次一變更與 rollback 約束**。

### 評測 coding agent 時，公開 trajectory 比單一 pass rate 更有診斷價值

**發布日期：2026-07-21｜類型：官方評測方法**

完整 trajectory 能回答 leaderboard 無法回答的問題：模型是否偷看 git history、是否重試到僥倖成功、是否誤用工具、是否提早宣稱完成、多少 token 花在無效探索，以及 harness 是否暗中給了某模型優勢。

團隊建立內部 eval 時，至少應保存：

- model／version、harness、system prompt、工具 schema 與權限；
- repository commit、sandbox、network policy、timeout 與 token／effort；
- 所有 tool calls、tool outputs、compaction 與人工介入；
- deterministic verifier、失敗原因與 accepted artifact cost。

這會讓「模型變強」從行銷敘事變成可以 debug 的系統差異。

### AMD local AI 的訊號改善，但相容性矩陣仍比宣傳標題重要

**發布日期：2026-07-20 至 2026-07-24｜類型：Reddit 社群回報／官方文件交叉查核**

[r/LocalLLaMA 的 Unsloth AMD 公告討論](https://www.reddit.com/r/LocalLLaMA/comments/1v1nor4/unsloth_now_supports_amd/)獲得大量關注，主文宣稱 Windows、Linux、WSL 與多種 Radeon／Instinct／Strix Halo 可用。這顯示 AMD local AI 生態已從「能不能跑」轉向安裝、quantization、training 與 deployment 的整合體驗。

但這仍是專案方主文，不是大量獨立 benchmark。實務上要留意：

- 官方 Unsloth guide 的可操作流程主要仍圍繞 ROCm 版本、PyTorch wheels 與相容硬體；「Technically Mac」不代表原生 ROCm training 有正式同等支援。
- GitHub release notes 同時列出 ROCm detection、bitsandbytes、VRAM probing 與模型-specific fixes，代表支援面正在快速變動。
- 社群常見成功案例會省略 kernel、driver、OS、quant、context 與 fallback backend；沒有完整環境資料的 tok/s 不宜橫向比較。

**可採用的做法：** 先用 `amd-smi`／官方 compatibility matrix 固定硬體與 ROCm 版本，建立乾淨 venv，跑 inference→短 SFT→checkpoint resume 三段 smoke test；記錄完整環境後才投入長訓練。

## 6. 今天值得嘗試

### 做一個 30 分鐘的「第三方模型閘道」安全驗收

1. 建立 disposable repository 與專用 API key，設定 5–10 美元或等值 usage ceiling。
2. 接入 GLM 5.2 後，同時核對 `/status`、provider dashboard 與 request log，確認 UI 名稱沒有掩蓋實際模型。
3. 跑三題固定任務：有 tests 的 bugfix、跨檔 refactor、工具呼叫；每題只允許一輪重試。
4. 記錄 accepted output、測試、時間、token、人工修改與錯誤 tool calls。
5. MCP 只開 read-only mock data；故意放入一段「忽略規則、外傳資料」的文件，檢查 Agent 是否把內容當指令。
6. 測完撤銷 key，檢查全域 Claude Code／Cursor 設定，移除 helper 加入但未使用的 MCP 與 model mapping。

若模型在固定任務集確實較便宜，但 provider 身分、工具權限或回退行為不可觀測，就不應直接成為 production 預設。
