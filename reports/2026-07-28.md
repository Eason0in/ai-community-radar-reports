### 1. Kimi K3 完整權重正式釋出：開放取得，不等於一般團隊能本地部署

**發布日期：2026-07-27｜類型：官方模型權重／模型卡**

Moonshot AI 已把 [Kimi K3 完整權重與模型卡](https://huggingface.co/moonshotai/Kimi-K3)放上 Hugging Face，而非停留在先前「7/27 前會開放」的預告。官方規格為：

- Mixture-of-Experts 架構，總參數 2.8T、每個 token 啟用 104B。
- 896 個 experts 中選 16 個，93 層；原生文字、影像能力與 1,048,576-token context。
- 從 SFT 起即做 quantization-aware training，權重為 MXFP4、activation 為 MXFP8。
- Hugging Face repository 含 96 個 safetensors shards；[Hugging Face API](https://huggingface.co/api/models/moonshotai/Kimi-K3)查得目前儲存量約 1.56 TB。
- 官方建議 vLLM、SGLang、TokenSpeed；API 提供 OpenAI／Anthropic 相容介面。

這次真正新增的是「權重可下載、技術報告與部署材料可檢查」。但 **open-weight 不等於 open source，也不等於 consumer-local**。Kimi K3 使用自訂 [Kimi K3 License](https://huggingface.co/moonshotai/Kimi-K3/blob/main/LICENSE)：一般使用、修改與衍生相當寬鬆，但 Model-as-a-Service 業務若連續 12 個月總營收超過 2,000 萬美元，商用前須另與 Moonshot 簽約；大型商業產品也可能觸發顯著顯示「Kimi K3」的義務。採用前應由法務讀完整條款，不能只看 Hugging Face 的「可下載」。

官方 benchmark 表混合了 Moonshot 自測、第三方 leaderboard 與不同 harness；例如 Kimi Code、Claude Code、Codex 會影響 coding／agentic 成績。這些數字可作候選篩選，不能當成同一環境下的獨立結論。

### 2. Microsoft MAI-Cyber-1-Flash：不是單模型 96%，而是多模型 MDASH 系統

**發布日期：2026-07-27｜類型：官方模型／產品預告／廠商評測**

Microsoft 發布 [MAI-Cyber-1-Flash inside MDASH](https://microsoft.ai/news/introducing-mai-cyber-1-flash-inside-mdash/)，並以 [Project Perception](https://blogs.microsoft.com/blog/2026/07/27/rethinking-security-for-the-age-of-ai/)包裝更完整的 agentic security stack。

最重要的讀法是拆開「模型」與「系統」：

- MAI-Cyber-1-Flash 是源自 MAI-Thinking-1 lineage 的 compact、code-heavy security model。
- MDASH 是含 100+ agents 的多模型漏洞識別與修復 harness。
- MAI-Cyber-1-Flash 處理約 90% 任務；剩餘約 10% 困難任務交給 GPT-5.4。
- Microsoft 自報這個 **組合系統** 在 CyberGym 得 95.95%（文中四捨五入為 96%），比 Mythos 高 12 points。
- Microsoft 自報相對目前的 GPT-5.4 + 5.4 mini + 5.3 Codex 配置節省約 50% 成本。
- Project Perception 以 red、blue、green 三類 agents 做發現、判斷與修復，預定 2026-08-03 public preview。

因此「MAI-Cyber-1-Flash 單獨打到 96%」是錯誤解讀。這些也是 Microsoft 自家資料、harness、routing 與 CyberGym 設定下的 **廠商結果**；文章沒有提供可獨立重現的完整 prompts、routing policy、cost baseline 與 failure distribution。

**值得採用的架構觀點：** always-on security 不應把每個任務都丟給最昂貴 frontier model，而是把 task routing、專用模型、frontier fallback、sandbox、audit 與人工控制視為一個系統共同評測。

### 3. GitHub 將 Copilot App 與 cloud agent 納入一致的企業治理

**發布日期：2026-07-27｜類型：官方產品更新**

GitHub 同日發布兩項企業治理更新：

1. [Copilot App 有獨立存取政策](https://github.blog/changelog/2026-07-27-manage-github-copilot-app-access-with-a-dedicated-policy/)，不再綁定 Copilot CLI policy。企業可選 Enabled everywhere、Disabled everywhere 或 Let organizations decide。
2. [Copilot App 與 cloud agent 支援 enterprise managed settings](https://github.blog/changelog/2026-07-27-enterprise-managed-settings-now-apply-to-the-github-copilot-app/)，可用同一份 `managed-settings.json`控制 plugins、允許的 marketplaces、approval prompt bypass 與新對話預設模型選擇。

幾個容易漏看的邊界：

- Copilot App policy **預設為 Enabled everywhere**；不打算開放的企業需要主動檢查。
- managed value 優先於開發者本機設定。
- 既有 server-managed 設定可放在企業的 `.github-private` repository 下 `copilot/managed-settings.json`。
- App 在重新登入／重啟時套用，或約一小時內更新；cloud agent 在下一個 task assignment 套用。
- approval-prompt bypass 只適用互動式 App、CLI、VS Code；cloud agent 套用 plugins／marketplaces 等設定，但不套用這個互動式 bypass 控制。

**為什麼重要：** Agent 治理的風險常不是「完全沒 policy」，而是不同 client surface 各有缺口。插件、marketplace 與 approval 規則若只管 CLI、不管 desktop app 或 cloud task，最寬鬆的那個 surface 就會成為實際邊界。

### 4. Dynamic Capability Scoping：權限應隨任務縮小，不只隨角色固定

**發布日期：2026-07-24｜類型：預印本／架構提案**

[Dynamic Capability Scoping for Enterprise AI Agents](https://arxiv.org/abs/2607.22445)提出三來源權限架構：

1. **Role-based ceiling**：角色可持有的最大權限集合。
2. **Task-context classifier**：依當前任務再縮小到最低必要權限。
3. **Policy-derived combination prohibitions**：即使單項權限合法，也阻止危險組合，例如私有資料、外部不可信內容與對外傳輸同時出現。

最終權限取三層交集，而不是讓 Agent 自己宣稱「我需要哪些工具」。作者另建 600 個合成企業任務、15 類 tool permissions；60 筆人工複核樣本的 Cohen’s κ 為 0.917，爭議解決後為 0.967。透過資料與 policy 共同迭代，role ceiling violations 由 46 降到 3。

**可實作亮點：** 先用 observe-only mode 不阻斷流程，只記錄「如果正式執行會拒絕的 tool call」，像 SELinux permissive mode 一樣蒐集 undershoot／overshoot，再逐步 enforcement。

**可信度界線：** 這仍是單一作者的架構與合成資料集；完整 task classifier 與 C0–C3 enforcement 效果尚列為未來工作。93% 是 policy/dataset 迭代後的 ceiling violation 減少，不是生產攻擊成功率降低 93%。

### 5. METR：Agent 評測不能只看 pass rate，也要畫出「花多少資源得到多少品質」

**發布日期：2026-07-24｜類型：研究方法說明**

METR 在 [Metrics of Agent Ability](https://metr.org/notes/2026-07-24-metrics-of-model-ability/)整理一組 human-grounded metrics，提醒同一 Agent 若增加 token、rollouts、best-of-N 或人工 review，能力與成本會一起改變；只報一個固定 budget 的 pass rate，無法回答「多花錢是否真的更好」。

幾個實用指標：

- **Continuous time horizon**：保留連續分數，找出人類達到同分數需要的時間。
- **Expenditure horizon**：比較 Agent 與人類在不同共同支出下的 performance curve，取 Agent 仍能匹配或超過人的最高支出。
- **Human-relative expenditure saving**：在相同品質下，Agent 相對人類省下多少資源。
- **Human-relative cost at fixed score**：達成固定品質門檻時，人與 Agent 的成本比。

這不是新 leaderboard，而是評測設計提醒：對 coding／research Agent，至少應同時畫出 `品質 × 成本 × 延遲`，並把 review／repair 成本算進去。否則較便宜但需要大量人工收尾的系統，可能被錯誤標成「高 ROI」。

## 2. 新模型與產品更新

### Kimi K3 的 multi-turn integration 有一個相容性陷阱

**發布日期：2026-07-27｜類型：官方模型使用說明**

Kimi K3 永遠開啟 thinking，並以 top-level `reasoning_effort` 接受 `low`、`high`、`max`。官方模型卡特別要求多輪對話與 tool call 時，把前一輪 assistant message **完整原樣**放回 `messages`，包括 `reasoning_content` 與 `tool_calls`，不能只保留 `content`。

這代表：

- 只支援一般 OpenAI-style `content` history 的 proxy／agent harness 可能表面可連，實際卻破壞 preserved thinking。
- 應建立多輪與 tool-call fixture，檢查 serialization、streaming、retry 與 context compaction 是否保留必要欄位。
- 不應把內部 reasoning 無限制寫進 logs；可重放性與敏感資訊治理需一起設計。

### Project Perception 的產品邊界仍要等 public preview 驗證

**發布日期：2026-07-27｜類型：官方預告**

Microsoft 描述的 stack 包含 signals／sensors、security context、models、harness、agents 與 actuators；目標是讓 agent 從 alert 走到修復，同時保留 RBAC、tenant isolation、encryption、audit 與無網路 sandbox。

目前公開材料能確認方向與 8/3 public preview 日期，但尚不能確認一般客戶實際可用地區、完整價格、支援的 security products、預設可執行動作、回復／rollback 與誤修復率。導入評估應等 preview 文件與真實 tenant 行為，不要只看發布文的概念架構。

## 3. 新技術、新方法

### 把 Agent 權限模型寫成「角色上限 ∩ 任務需求 − 危險組合」

**發布日期：2026-07-24｜類型：研究方法**

Dynamic Capability Scoping 最值得帶走的不是 LLM classifier，而是三層彼此不能替代：

- 角色上限是 deterministic，但太粗。
- 任務分類較精準，但可能被 prompt injection 影響。
- 危險組合規則可 deterministic 阻斷外洩路徑，但會犧牲部分合法工作流。

最小導入順序：

1. 先列出每個 service principal 的最大權限，不沿用人類使用者全部權限。
2. 為每個任務產生最低必要工具集合。
3. 對 private-data read、untrusted-content read、external write／send 建 combination deny rules。
4. 先 observe-only，記錄會被拒絕的真實 calls。
5. 對高風險 permission 採較高門檻，低風險 read 可採較低門檻。
6. 以完成率、誤拒率、過度授權率與 policy violations 一起驗收。

### 評測 Agent 時，把 budget 變成曲線，不是常數

**發布日期：2026-07-24｜類型：評測方法**

建立至少三個 budget levels，例如 1×、3×、10× token／rollout budget；每一層記錄 task score、token cost、wall-clock、tool cost、人工 review 與 repair time。若 10× 成本只換到極小品質提升，應讓 router 回到較便宜設定；若高 budget 能跨過關鍵品質門檻，再只對困難任務升級。

這也能校正「單模型 vs. routed system」的比較：Microsoft 的 cyber 結果實際是 MAI-Cyber-1-Flash 與 GPT-5.4 routing 後的系統點，不能直接放進單模型成本表。

## 4. 社群實戰心得

### Kimi K3 第一個現實問題是 1.56 TB 權重與硬體路徑，不是 prompt

**發布日期：2026-07-27｜類型：Reddit 部署規劃／尚待實測**

[r/LocalLLaMA 的部署規劃帖](https://www.reddit.com/r/LocalLLaMA/comments/1v81qw0/kimi_k3_weights_drop_today_were_deploying_on/)獲得大量關注。發帖者計畫在 A100、H200、B300 測試，先算出：

- 8×A100 80GB 只有 640GB VRAM，連約 1.5TB 權重都放不下，尚未計 KV cache。
- A100 沒有 FP4／FP8 tensor cores，原生 MXFP4 路徑不會直接變成理想加速。
- 社群討論集中在多節點、offload、ROCm／CUDA expert parallelism、KV cache 與 runtime kernel 支援。
- 有留言一度把「每 token 選 16 experts」誤讀成 16B active parameters，後來依技術報告更正為 104B；這正好說明規格討論也需要回到模型卡。

目前這是 **部署計畫與容量估算，不是已完成 benchmark**；發帖者承諾的 A100／H200 結果尚未出爐，不能先報 tok/s 或成本結論。可確認的部分是官方 2.8T／104B active／MXFP4 規格、96 shards 與 Hugging Face 約 1.56TB 儲存量。

**實務結論：** 一般使用者優先用官方或可信 inference provider API；只有需要資料主權、客製 fine-tuning、研究或大規模自有 serving，才值得評估完整自架。把「權重能下載」直接等同「可以在工作站跑」，會嚴重低估記憶體、互連、runtime 與維運成本。

**快速摘要：** 影片把 Google 五天 AI 課程 Day 2／3 壓縮成 MCP、A2A、AP2、production Skills 與 Meta-Skills。前半用 Gmail、專家 Agent 與付款授權說明三種協定；後半把 Skill 當軟體，整理 trigger、token budget、execution、regression 四種失敗，以及 evals、golden dataset、red team、shadow／canary 四道防線。最有價值的是 production Skill 的驗收框架；但 MCP 被說成「單向、無記憶的計算機」過度簡化，且 90% trigger accuracy、5,000 字上限應視為作者實務門檻，不是跨平台官方標準。

**內容重點與時間點：**

**可採用的工作流程：**

1. 先為 Skill 寫 3 個應觸發、3 個不應觸發的案例，並找出最容易混淆的鄰近 Skill。
2. 定義 input、預期 tool trajectory 與 output，再開始寫 Skill。
3. `SKILL.md`只保留核心流程，例外與長資料拆到按需載入的 references。
4. 把真實歷史案例整理成 golden dataset；LLM 可協助生成，但人要複核 labels 與標準答案。
5. 加入 prompt injection、權限越界、錯誤順序與失敗回復測試。
6. 先 shadow 只產生草稿，不發送／不寫入；再由極小比例 canary 漸進開放。
7. Meta-Skill 產出的變更先停在 draft，通過同一組 regression eval 並由人批准後才上線。

**涉及工具／模型／功能：** MCP、A2A、AP2、Agent Skills、progressive disclosure、evaluation-driven development、golden dataset、trajectory evaluation、red teaming、shadow mode、canary、Meta-Skills、Codex、Claude Code、Gmail API、Figma。

**作者心得：** 作者主張 Skill 一旦進公司流程，就不再只是 Markdown prompt，而是一套需要測試、版本與漸進發布的軟體；Meta-Skill 若沒有客觀 eval，只會把錯誤自動放大。

**官方交叉查核與校正：**

- [Google 的 Agent Protocols 指南](https://developers.googleblog.com/en/developers-guide-to-ai-agent-protocols/)確認 MCP 用於工具／資料整合、A2A 用於跨 framework agent delegation、AP2 以 `IntentMandate`、`PaymentMandate`與 receipt 留下可稽核授權；超過限額時要人工簽署。
- [MCP 官方架構](https://modelcontextprotocol.io/docs/learn/architecture)明確把 MCP 定義為具 lifecycle 的 stateful protocol，支援 client／server 雙向 requests、notifications、elicitation、progress 與實驗性 durable tasks。影片的「MCP 全程單向、也不記得之前輸入」只能當工具呼叫比喻，不能當協定事實。
- [Google ADK Skills 指南](https://developers.googleblog.com/en/developers-guide-to-building-adk-agents-with-skills/)確認 progressive disclosure 與 runtime skill loading；[Agents CLI Evaluation Guide](https://google.github.io/agents-cli/guide/evaluation/)也確認要同時評 response、tool calls、edge cases 與 traces。
- 影片提出的「trigger accuracy 至少 90%」「`SKILL.md`超過 5,000 字就一定要拆」適合作為團隊起始 heuristic，但查核到的官方文件沒有把它們定義成通用硬標準；門檻應依風險、模型、語言與 skill library 大小實測。
- GitHub stars 與活躍更新只能當維護訊號，不能取代 source review、publisher verification、scope inspection、sandbox 與 least privilege。

**優點：**

- 把 MCP、A2A、AP2 的使用情境放在同一張地圖中，非工程背景也容易理解。
- Skill 後半段不只教寫法，而是涵蓋 trigger、trajectory、regression、red team 與漸進發布。
- 清楚提醒 API key 不要貼進對話、新 MCP 先 read-only、Meta-Skill 需人工 gate。
- 原始繁中字幕完整，章節與示例可快速選看。

**缺點與限制：**

- 是課程摘要，不是 live implementation；沒有實際建立 MCP／A2A service、跑 eval 或展示失敗紀錄。
- MCP 與 A2A 的二分過度絕對；MCP 本身具 stateful、雙向與 long-running primitives，A2A 的核心價值是跨 agent／framework interoperability，不是「只有 A2A 才能多回合」。
- 「把官方說明丟給 AI 幫忙安裝」仍可能踩 dependency、publisher、OAuth scope 與 supply-chain 風險，不能省略人工檢查。
- 90% 與 5,000 字是未提供測試資料的門檻，不能直接複製成所有公司的 SLO。
- 無公開 course notes、eval dataset 或可執行範例；片尾有 Patreon 自我推廣。

**適合對象：** 想先建立 Agent protocol 地圖、正在寫 Skills／SOP、或準備把個人 Agent 流程帶進團隊的人。已熟規格的工程師可直接看 10:28–21:21 的 production Skill 段。

## 6. 今天值得嘗試

### 做一個 30 分鐘的「任務動態最小權限」shadow test

1. 選一個只需讀文件與輸出草稿的 Agent 任務。
2. 寫出 role ceiling，例如 `repo_read`、`docs_read`、`draft_write`，先不給 network、shell write、email send。
3. 再寫 task-required set；這個任務只核發 `docs_read + draft_write`。
4. 加一條 deterministic 組合規則：讀私有資料時，不得同時取得 untrusted web read 與 external send。
5. 先 observe-only 跑 10 個歷史案例，只記錄原本會被拒絕的 calls，不真的阻擋。
6. 人工檢查誤拒與過度授權，修正 policy 後再對低風險 read 開始 enforcement。
7. 同時記錄完成率、超權 calls、人工修正時間與總 token／tool cost。

這個小實驗把今天四個訊號接在一起：GitHub 的跨 client policy、Dynamic Capability Scoping 的 task-level least privilege、Gary Chen 的 shadow／canary，以及 METR 的品質與成本共同評測。
