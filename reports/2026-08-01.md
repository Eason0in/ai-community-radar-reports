### 5) Tailscale 復盤 Hugging Face 入侵：不是 VPN 漏洞，而是 136 個長效密鑰與可重用 auth key

- **發布日期：2026-07-31**
- Tailscale 表示事件沒有利用其產品漏洞；Agent 在先取得 production worker code execution、Kubernetes root 與 secret store 後，讀到 136 個 keys，其中一把可重用 Tailscale auth key 被拿到外部 sandbox，數日內註冊了 181 個帶 CI tag 的 nodes。
- 具體修法是用 workload identity federation 讓 CI 以雲端 identity 換短效 credential，不讓可攜式長效 key 存在；再以 flow logs＋SIEM 從連線另一端偵測異常，以 Tailnet Lock、窄 tags、one-off keys 與 device posture 限制 blast radius。
- 這是對先前事件的**廠商自我復盤與防護建議**。它新增的價值是把「zero trust 為何沒有阻止 lateral movement」拆成 credential lifecycle、node admission 與 detection 三層，而不是把責任簡化成單一工具是否有 CVE。
- 來源：[Tailscale 技術復盤](https://tailscale.com/blog/hugging-face-intrusion)、[Hugging Face 事件重建](https://huggingface-anatomy-of-frontier-lab-model-intrusion.static.hf.space/index.html)

## 3. 新技術、新方法

### Equal-token 實驗：Self-Refine／Reflexion 不一定比多抽幾次更有效

- **論文日期：2026-07-30；預印本**
- 研究在 1.5B、3B、7B 開放模型、兩個數學 benchmark、每組 150 題上，比較七種方法；把 critique、reflection、debate、selection 的所有輸出 token 都計入，再以相同實測成本對比 repeated sampling＋majority vote。
- 36 組配對比較中沒有方法可靠勝過 repeated sampling；10 組顯著更差，且 18 組「模型檢查自己的輸出」比較全為負。7B 上 Self‑Refine／forced Reflexion 仍低 3.6～10.1 points。
- **可用方法：**任何「自我反思提升 X%」的流程，都加一個等 token、等模型的 repeated-sampling baseline；若沒有成本相等與信賴區間，不能確定提升來自方法還是多花 token。
- 限制是小模型、數學題與 150 題規模，不能直接外推到 frontier agent 或程式修改；優點是作者公開 code、prompts、generations 與 verification scripts。
- 來源：[arXiv:2607.28576](https://arxiv.org/abs/2607.28576)

### Computer-use benchmark 的 FAIL 中，15.3% 可能是評分或題目錯

- **論文日期：2026-07-30；預印本**
- 研究人工稽核五個 web、enterprise workflow、desktop-control benchmarks 的 150 條公開 FAIL trajectories，發現 10.7% 是 evaluator false negative、4.7% 是 broken task，合計 15.3% 被錯判。
- 真正失敗裡，verification／feedback 與 planning 問題多於 execution／grounding；只報單一 success rate，會看不出是 Agent 沒做成、觀察資料漏掉關鍵畫面、替代路徑被 oracle 拒絕，還是任務本身已 stale。
- **可用方法：**保留 decisive screenshots／DOM state、接受多種有效終態、定期重跑 task health、對 FAIL 抽樣人工稽核，並分層報 planning、grounding、verification 錯誤。
- 來源：[arXiv:2607.28367](https://arxiv.org/abs/2607.28367)

### ORCA-bench：前沿 Agent 在擬真 on-call RCA 的 realistic setting 最好只有 25.3%

- **論文日期：2026-07-30；預印本**
- ORCA-bench 提供 50 GB、六天的 OpenTelemetry metrics／logs／traces、Prometheus、Jaeger、OpenSearch／Grafana 與完整 source code，共 1,079 個 root-cause-analysis 任務；ground truth 經 SRE 確認，LLM judge 再由人類複評，weighted Cohen's kappa 為 0.90。
- 五個 frontier agents 中，Medium realistic-input 最佳 RCA accuracy 25.3%，Hard 10.0%；最弱模型有 40% incident reports 產生不合理 root cause，拿掉 source code 後所有指標都下降。
- **判讀：**這仍是可控、公開、逐題獨立調查的 testbed，真實 production 通常更大、更動態、更有組織特例。因此目前較安全的角色是收集證據、建立候選 root cause 與執行 read-only 查詢，不是自動接管 remediation。
- 來源：[arXiv:2607.28545](https://arxiv.org/abs/2607.28545)、[公開 benchmark](https://hub.harborframework.com/)

## 4. 社群實戰心得

### GPT‑5.6 降價後，真正難題變成 routing 與返工成本

- **討論日期：2026-07-30～2026-07-31**
- Hacker News 討論的共識不是「所有工作換 Luna」，而是規格明確、容易驗證的任務較適合便宜模型；複雜 codebase 的實測回報互相矛盾，有人把 Luna xhigh 當 daily driver，也有人認為錯誤註解與錯誤實作會污染後續 context。
- 最可操作的模式是「強模型 sandwich」：強模型定義計畫與 acceptance criteria，便宜模型實作，強模型或 deterministic tests 做最後 review。它仍需和單一強模型 baseline 比較，否則 orchestration overhead 可能吃掉節省的 token。
- 這是**社群經驗，不是受控評測**；討論熱度只能說明 routing 問題受到關注，不能證明任何模型的普遍優劣。

### 把 Agent 指令檔視為可測的產品，而不是越積越長的筆記

- Anthropic 與 OpenAI 官方文件都建議讓 `CLAUDE.md`／`AGENTS.md` 保持短、準確，將重複工作做成 skill，把必須強制的安全限制交給 permissions、hooks 或 CI。

**快速摘要**

這是一套「先用 `/init` 建起點、再刪可自動發現資訊、補隱性規則、最後持續修剪」的指令檔維護法。最有價值的不是格式模板，而是把內容分流到 nested instructions、skills、hooks／CI，避免 always-on context 變成過期文件與安全假象。

**內容重點**

1. `00:34–04:06` 區分 user、project、nested scope；規則越靠近實際工作範圍，越適合放局部檔案。
2. `04:06–07:25` 用 `/init` 建 starter file，但以三問刪減：模型能否自行發現、是否多數任務都需要、數月後是否仍成立。

6. `13:19–14:47` 作者實測健檢抓到文件衝突、過長測試流程與 `CLAUDE.md`／`AGENTS.md` 重複維護問題。

**建議實作工作流程**

1. 從 repo root 執行 `/init`，把輸出當草稿。
2. 刪除 package manager、目錄結構等能從 repo 快速查到且容易過期的描述；保留正確 build／test 命令與真正的專案慣例。
3. 將只適用子目錄的規則移到 nested file；將發布、review 等長流程做成 skill。
4. 將 secret scanning、禁止路徑、格式與測試門檻放進 hooks／CI；指令檔只說明意圖與正確入口。
5. 用兩三個代表性任務做 A/B：修改前後是否少犯錯、token 是否下降、重要規則是否更常被遵守。
6. 每逢模型、架構或工作流程更新，檢查衝突與 stale rule；沒有證據支持的規則就刪。

**工具／模型／功能**

- Claude Code：`CLAUDE.md`、`CLAUDE.local.md`、nested files、`/init`、`/insights`、skills、hooks

**建議測試工作流程**

1. 先用三個固定任務：一個單頁 app、一個既有 repo bug、一個工具／3D 任務。
2. 固定模型版本 `DeepSeek‑V4‑Flash‑0731`、reasoning effort、max tokens、Codex 版本與 clean workspace。
3. 每題保存 prompt、完整 trajectory、diff、token usage、wall-clock time 與 API cost。
4. 以自動測試、操作腳本、geometry／compile checks 評分，不只看畫面「像不像完成」。
5. 每題至少跑三次，分開計算 first-pass success、修一次後成功率與人工修正分鐘數。
6. 再與 Luna、Terra、Kimi 或其他候選用同一 harness 比較；避免把模型、工具與前一輪 context 一起改。

**缺點與限制**

## 6. 今天值得嘗試

### 60 分鐘：建立你的「模型 routing＋指令檔」最小實驗

1. 選一個 30～60 分鐘可人工完成、已有測試的真實小任務。
2. 把 `AGENTS.md`／`CLAUDE.md` 縮到只留不能從 repo 推斷的規則與完成條件；安全限制交給 CI／hook。
