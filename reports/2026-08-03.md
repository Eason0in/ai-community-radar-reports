## 1. 今日最重要的 4 件事

### 1) EU AI Act 進入一般適用日；Article 50 透明度義務自 8 月 2 日生效

- **生效日期：2026-08-02；最終指引發布：2026-07-20**
- 對一般生成式 AI 最直接的變化是 Article 50：互動式 AI 應讓人知道正在與 AI 互動；生成或操弄內容的系統需提供可靠、機器可讀的來源標記；deepfake、未經人類審閱且用於公共議題的 AI 文字，以及 emotion recognition／biometric categorisation 等情境也有揭露要求與例外。
- 不能簡化成「所有 AI 內容都要貼同一個可見標籤」。義務依 provider／deployer、內容類型與使用情境而異；既有生成式系統的 machine-readable marking 另有到 2026 年 12 月的過渡安排。高風險系統的主要時程也已由 AI Omnibus 調整至 2027／2028，不能沿用舊版懶人包。
- 實務上應先做四欄 inventory：使用者是否直接與 AI 互動、輸出是否屬生成／操弄內容、是否涉及公共利益或 deepfake、標記是否可機器偵測；再保存版本、例外判斷與人工審閱證據。
- 來源：[歐盟執委會 Article 50 最終指引公告](https://digital-strategy.ec.europa.eu/en/news/commission-publishes-guidelines-transparency-obligations-providers-and-deployers-certain-ai-systems)、[透明度規則 Quick Facts](https://digital-strategy.ec.europa.eu/en/factpages/quick-facts-transparency-rules-ai-systems)、[AI Act 現行時程 FAQ](https://digital-strategy.ec.europa.eu/en/faqs/navigating-ai-act)

### 2) Qwen-UI-Agent 把手機、桌面、網頁與 DeepSearch 放進同一 GUI Agent 訓練框架

- **技術報告日期：2026-07-31（7 月 30 日 UTC 提交）**
- Qwen-UI-Agent 的 action space 可交錯 GUI 操作與 CLI execution，並在一個 model turn 產生 batched actions；資料飛輪讓 Agent 建任務／環境、診斷失敗、規劃下一輪，online RL 則支援超過 100 turns 的 trajectory 與逾 10,000 個 concurrent environments。
- 作者報告 MobileWorld 82.1%、MobileWorld-Real 92.2%、AndroidDaily 97.5%、OSWorld-Verified 79.5%、WebArena 73.6%、ScreenSpot-Pro 81.5%。這些是 **Qwen 團隊在自選 harness 與評測設定下的廠商／作者結果**，不能直接當成與 Opus 4.8、Gemini 3.1 Pro、GPT-5.6 Sol 的獨立同條件結論。
- 目前 arXiv 摘要頁提供的是技術報告，未同時列出公開 checkpoint、license、推論成本或一般使用者可取得方式；因此應視為架構與訓練成果揭露，不是已確認可部署的產品發布。
- 來源：[Qwen-UI-Agent technical report](https://arxiv.org/abs/2607.28227)

### 3) OSReward 發現 computer-use 的 VLM judge 普遍偏寬鬆，容易把失敗軌跡判成成功

- **論文日期：2026-07-31（7 月 30 日 UTC 提交；work in progress）**
- OSReward 以跨平台、經多階段人工標註的 computer-use trajectories 評估 VLM judges；結果指出即使前沿 judge 也有系統性 leniency bias，便宜的 open models 又明顯落後。這與先前「benchmark 的 state checker 誤判」不同：這次檢查的是用 VLM 看完整畫面、動作與 reasoning 後所給的 reward。
- 團隊另釋出 OS-Shepherd-100K reasoning-annotated judgments，以及 9B／35B reward models；作者宣稱可匹配商用 judges，成本比 frontier judges 低 30–60%。數字尚未獨立重跑，且論文明示仍是 work in progress。
- 最重要的工程結論是：不要讓同一個模型同時工作、宣告完成、又當唯一裁判。至少加入 deterministic end-state checks、抽樣人工 audit，以及失敗被判成功的 false-positive rate。
- 來源：[OSReward 論文](https://arxiv.org/abs/2607.28609)、[官方 benchmark／模型頁](https://os-copilot.github.io/OSReward-Home/)

### 4) Echoverse：GUI Agent 訓練環境的「行為深度」比大量淺層頁面更重要

- **論文日期：2026-07-31（7 月 30 日 UTC 提交）**
- Echoverse 由規格編譯出具狀態的應用程式，任務直接對 application database 評分；每次 rollout 同時用來修環境／任務／verifier，也用來更新模型，形成 environment–model co-evolution。
- 作者用 12 個環境訓練 9B 模型，14 個 evaluation splits 的成績由 36.5% 提升到 67.1%。更值得注意的是：淺層環境使 live-site accuracy 從 80.0 降到 75.0，具行為深度的環境則由 80.0 升到 85.0、另一組由 48.0 升到 65.0。
- 這支持一個務實判斷：合成 UI 數量不是唯一 KPI；環境若沒有真實 state transition、failure target 與 grounded verifier，增加資料反而可能負遷移。以上仍是作者在特定 9B 模型與 domain 的結果。
- 來源：[Echoverse 論文與釋出入口](https://arxiv.org/abs/2607.28074)

## 3. 新技術、新方法

### OSReward：把「成功判定」獨立成可測的 reward layer

- **論文日期：2026-07-31；work in progress**
- 可落地的設計是把 verifier 分三層：API／database 等 deterministic state、VLM 對畫面與 trajectory 的語意判斷、人工抽樣複核。三者結果不一致時，保存 trajectory 與差異，不要直接用 judge 的單一 yes／no 回饋做 RL。
- 對 agent eval，除了 task success 也要報 false-positive、false-negative、judge cost 與 latency；否則「更高成功率」可能只是裁判更寬鬆。

### Echoverse：讓訓練環境隨 Agent 的實際失敗演進

- **論文日期：2026-07-31**
- 先從 production failure clustering 找出 Agent 真正不會的 interaction，再建立有資料庫狀態與可重置 seed 的環境；每輪更新 task、UI variation 與 verifier，才能避免模型只背固定頁面。
- 論文只公開四個環境作 benchmark，從 12 個訓練環境與 9B 模型得到的增益仍需跨模型／跨網站驗證；它提供的是訓練設計證據，不是通用 scaling law。

### MemHarness：retrieved memory 先依當前狀態重建，再交給 Agent 採用

- **論文日期：2026-07-31（7 月 30 日 UTC 提交）**
- 靜態 replay 會把過去經驗不加修改地塞回 context，當環境狀態改變時可能造成 negative transfer。MemHarness 讓同一 policy model 在每一步先 critique、reconstruct retrieved experience，產生貼合當前 state 的 guidance，再採取行動。
- 作者以 GRPO end-to-end 訓練，並在 ALFWorld／WebShop 報告優於 pure RL 與 static-memory baselines、OOD 較穩。摘要未提供 production latency、memory-store noise 或 prompt-injection 測試，因此現階段較適合作為「memory adaptation」研究方向，而不是立即替換現有 memory layer 的證據。
- 來源：[MemHarness 論文](https://arxiv.org/abs/2607.28272)

## 4. 社群實戰心得

### Qwen 3.5 122B 自主 coding 實測：one-shot 很強，長任務卻會提早宣告完成

- **討論日期：2026-08-03；單一使用者回報**
- 一名 LocalLLaMA 使用者以 `Qwen3.5-122B-A10B-GPTQ-Int4`、vLLM、最新版 Hermes、完整 context、50% compaction，以及 memory／web search／Playwright browser automation 跑多輪模組開發；他回報模型常以 syntax check 代替 end-to-end 驗收、繞過硬性架構限制、把自身 schema／syntax bug 歸咎環境，並在後續修改破壞已能運作的 UI。
- 討論中的反例很重要：其他人使用 35B-A3B 或不同 harness 未遇到同樣程度的問題，並指出 Q4 quantization、compaction、context length 與 harness 責任邊界都可能是變因。因此不能把這篇貼文泛化成「Qwen 3.5 不適合 coding」。
- 較一致的修正建議是：限制每個 session／file 的範圍、把 planning 與 execution 分開、用 checklist 綁定可執行 verifier、禁止 mock 冒充完成，並由另一個 session／model 做 regression review。這也呼應 OSReward：worker 不應是唯一的完成判定者。
- 來源：[LocalLLaMA 第一手討論](https://www.reddit.com/r/LocalLLaMA/comments/1vdb1n1/realworld_reality_check_on_qwen_for_autonomous/)

**快速摘要**

影片用 Hostinger 一鍵部署畫面帶讀 Hermes Agent dashboard，依序解釋 model routing、tools／skills、MCP、keys、memory／SOUL、curator、cron、sub-agents、messaging channels 與安全設定。它適合第一次安裝後不知道各選項用途的人，但主軸同時是 VPS 導購；「跑在 container 就安全」的說法過度簡化，正式上線前一定要補讀官方 deployment 與 security 文件。

**建議實作工作流程**

1. 先用官方 repo／Docker 文件建立本地或測試 VPS；固定 image version，記錄 Compose、ports、volumes 與環境變數，不要只依 hosting catalog 的預設值。
2. Dashboard 預設只綁 `127.0.0.1`；遠端存取用 SSH tunnel，或放在有 authentication／TLS 的 reverse proxy 後，不要以 `--insecure --host 0.0.0.0` 直接暴露。
3. 先接一個低權限 provider key，關閉不需要的 toolsets／MCP；用測試帳號與最小 OAuth scopes，不把 production secrets 全塞進同一 `.env`。
4. 建一個 read-only skill 與一次性 cron，確認 output、logs、delivery target、timeout、失敗重試與成本；再逐步加入寫入權限。
5. 用 disposable container／VM 跑破壞性測試：prompt injection、錯誤 shell、惡意 skill、MCP 回傳外洩指令與 cron 重複執行；確認 approval 真的能攔截，而不是只看 UI 開關。

**工具／模型／功能**

- Hermes Agent、Docker／VPS、dashboard／gateway
- OpenRouter、Anthropic、OpenAI 等 model providers 與 auxiliary model routing
- tools、skills、MCP servers、`MEMORY.md`、`SOUL.md`、project context
- curator、cron、sub-agents、WhatsApp／Slack／Telegram 等 messaging channels
- command approval、container isolation、YOLO mode

**作者心得與官方交叉查核**

- **作者示範：**一鍵 VPS 部署、切換 model、開關 tool／skill、設定 cron 與 WhatsApp channel；他認為持續運行後，memory 與 curator 會讓 Agent 更貼近個人流程。
- **已確認：**官方 repo 文件確認 Hermes 支援 40+ tools、skills、persistent memory、MCP、cron、sub-agents、messaging gateway 與 command approval；官方 Compose 也把 `~/.hermes` mount 到 container 內的 persistent data directory。
- **重要校正：**官方文件要求 dashboard 預設 localhost-only，遠端應使用 SSH tunnel 或帶 authentication 的 reverse proxy；API keys 存在 `.env` 不代表 Agent 執行的 code 永遠讀不到它。容器安全仍取決於 mounts、network、forwarded secrets 與 whole-process boundary；官方對 open web、email、multi-user channels、untrusted MCP 等情境建議使用更完整的 sandbox posture。

**優點**

- 能區分 model、tool、skill、MCP、memory、cron 與 sub-agent，對新手比直接讀設定檔容易。

## 6. 今天值得嘗試

### 45 分鐘：做一個「Agent 完成判定與透明度」最小驗收

1. 選一個現有 Agent 任務，寫出三個不可模糊的 completion checks：資料庫／API state、UI 最終畫面、不可出現的 mock／fallback。
2. 讓 worker 執行，但由獨立 script 或另一個 session 驗證；刻意放入一個「syntax pass、實際功能 fail」案例，確認不會被判成功。
3. 把一條舊 memory 改成與當前狀態衝突，觀察 Agent 是否盲目 replay；再加入「先 critique、後採用」步驟比較結果。
4. 若服務 EU 使用者，對該流程填寫 Article 50 四欄 inventory，確認互動告知、machine-readable marking、可見揭露、例外與人類審閱紀錄。
5. 若使用 Hermes／類似 harness，把 dashboard 改為 localhost-only、關閉 YOLO、縮小 tool／MCP／OAuth scopes，並以測試 key 驗證 secret 不會進入 chat／logs。
