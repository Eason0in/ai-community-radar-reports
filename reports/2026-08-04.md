### 1) Qwen3.8-Max 正式亮相，但「開放權重」仍要等下週

- **發布日期：2026-08-03**
- Qwen 官方宣布 Qwen3.8-Max，稱其為目前最強模型；官方貼文列出 **2.4T 總參數、95B 啟用參數**，並預告下週釋出 Qwen3.8-Max 與 Qwen3.8-27B 權重。[官方公告](https://x.com/Alibaba_Qwen/status/2084100707423289643)｜[官方介紹頁](https://qwen.ai/blog?id=qwen3.8)
- 截稿時，Qwen Cloud 文件仍列出 `qwen3.8-max-preview`，標示 **1M context、支援 thinking 與 tools**；Qwen 的 Hugging Face 模型庫尚查不到 Qwen3.8 權重。因此今天能確認的是「正式公布與排定釋出」，不是「權重已可下載」。[Qwen Cloud 模型文件](https://docs.qwencloud.com/developer-guides/getting-started/text-generation-models)｜[Qwen Hugging Face](https://huggingface.co/Qwen/models)
- 官方展示的 benchmark 與長時間自主工程案例皆屬**廠商結果**；模型卡、授權、實際權重與第三方重跑尚待釋出後驗證。

### 2) OpenAI 公開 GPT-Live 的全雙工語音架構

- **發布日期：2026-08-03**
- OpenAI 說明第三代 GPT-Live：語音主路徑可持續聽與說，另以非同步方式委派前沿模型處理較難問題，因此不必先用 turn detector 切斷使用者，也不必在長推理時讓語音停住。[OpenAI 工程文章](https://openai.com/index/continuous-voice-interaction-with-gpt-live/)
- 關鍵工程不是只有模型：媒體前端由 Python asyncio 改寫成 Go、WebRTC 啟動由 WARP 簡化、工具走非同步 RPC；長對話則先暖機替代 instance、預填目前 context、平行推理再切換，同一機制也用於不中斷的 context compaction。
- 這套系統已支撐 ChatGPT Voice；文章稱 GPT-Live API 將推出，但**尚未提供確切公開日期、價格或完整可用地區**。延遲數據為 OpenAI 自家生產環境結果。

### 3) SafeKeep 指出：工具 schema 本身可能削弱模型拒絕危險請求的能力

- **發布日期：2026-07-31**
- 論文發現，agent 看到 schema 化工具規格時，內部拒絕訊號可能被削弱。SafeKeep 先用攤平的文字版工具規格做安全判斷，真正執行時才保留原 schema。[論文](https://arxiv.org/abs/2607.29254)
- 作者在 2 個 benchmark、4 個 LLM 上報告：有害請求拒絕率由 23.8% 升至 70.6%，prompt-injection attack success rate 由 25.6% 降至 2.5%。這是**論文作者結果**，但直接提醒 agent 開發者：工具描述、判斷介面與執行介面不應視為同一層。

### 4) ARCTIC 把 AI code review 從「找 bug」擴成「還原意圖、偵測漂移」

- **發布日期：2026-07-31**
- ARCTIC 以 18,000 次 code review 建立分類法，從工作紀錄與 metadata 推測原始意圖，再用 back-translation 檢查 diff 是否偏離，並排序真正值得人看的區段。[論文](https://arxiv.org/abs/2607.29516)
- 作者報告 intent prediction F1 0.86、drift detection QWK 0.907，且 code spotlight 用五分之一 token 達到 2.4 倍基線品質；這些仍是**作者／部署方數據**。實務價值在於把 reviewer 的第一問改成：「這個 diff 是否忠於需求？」而不只問語法是否正確。

### 5) 新研究提醒：AI safety benchmark 的排名很容易被題組與模型面板扭曲

- **發布日期：2026-07-30**
- 研究重跑 R-Judge、InjecAgent、AgentHarm、AgentDojo 等四套 agent safety benchmark，指出小型或能力差異過大的模型面板會放大假訊號；在 R-Judge 上，永遠回答正類的 baseline，F1 甚至高於 21 個具判別力模型中的 5 個。[論文](https://arxiv.org/abs/2607.28685)
- 作者建議任何「更安全」結論至少同時交代 benchmark、metric、目標行為與 model panel。看到單一總分或廠商排行榜時，先不要把它外推成一般安全能力。

## 3. 新技術、新方法

### Agent 安全：把離散決策與連續數值一起驗證

- **2026-07-31｜CAGE：**一般 certificate 各自安全，不代表組合後仍安全。CAGE 同時列舉 agent 的離散分支並驗證連續擾動；作者稱在合成、政策、監管與真實交易案例中消除預算內 false allow，但會犧牲部分可自動執行比例。[論文](https://arxiv.org/abs/2607.29190)
- 可操作解讀：付款、退款、權限與合規 agent 不要只驗證「模型輸出」；要把分支條件、數值邊界、工具副作用與最終授權一起測。

### Agent 記憶：來源標記不能在摘要／合併時消失

- **2026-07-31｜PPMF：**論文展示 memory consolidation 可能把「外部低信任觀察」重寫成「使用者偏好／既定流程」，留下動作觸發詞卻洗掉來源。PPMF 以 middleware 保留平台級 provenance、動作風險與授權資訊。[論文](https://arxiv.org/abs/2607.29167)
- 作者測試中，未加防護的 attack success rate 最高達 1.0；加入 PPMF 後，評估的未授權高風險動作沒有通過。仍屬作者設計與測試結果，實務上可先把 `source`、`trust_level`、`authorized_actions` 做成不可由模型摘要覆寫的欄位。

### Coding agent 評測：模型與 harness 要拆開報

- **2026-07-30｜Model or Harness：**研究整理 41 種 coding-agent failure mode，沿互動邊界與責任方分類；最強自動 judge 與人類標註的一致度 κ=0.76。[論文](https://arxiv.org/abs/2607.28802)
- 報 benchmark 時至少固定模型 endpoint、prompt、工具權限、context、retry／budget、測試環境，否則「模型進步」可能只是 harness 換了。

## 4. 社群實戰心得

### Qwen3.8 的長程 demo，引發「究竟模型還是腳手架在工作」的質疑

- **討論日期：2026-08-04｜來源：Reddit r/LocalLLM**
- 討論串聚焦官方宣稱的 10+ 天自主軟體工程與 500+ turns 晶片優化案例；社群最具體的提醒是：長 trace 很難人工讀完，真正要看的是「誰在驗證、何時停止、失敗如何暴露」。[討論串](https://www.reddit.com/r/LocalLLM/comments/1ve33xi/did_anyone_actually_read_the_qwen_38max_blog/)
- 一位 benchmark 建置者披露：同一模型、同一 endpoint，在 25 個真實 merged PR 上由兩套 harness 執行，完成數是 24 對 19。這是**自家 benchmark、n=25 的單一案例**，不能證明普遍差異；但與今天的 Model-or-Harness 研究一致：廠商同時提供模型與 scaffolding 的 demo，無法單獨歸因模型能力。
- **採用建議：**比較模型時保留完全相同的 harness 與 budget；比較 agent 產品時，另列工具、retry、context 管理與 verifier，別只抄模型名稱。

### Gary Chen｜《Google AI 課程 Day 4+5 解析，怎麼放心讓 AI 上正式環境？》

- **發布日期：**2026-08-02
- **查核時數據：**11,332 次觀看；16:52；公開影片（2026-08-04 08:09 CST）
- **連結：**[YouTube](https://www.youtube.com/watch?v=h7abDtqN9gs)
- **字幕：**已完整閱讀人工繁體中文字幕。
- **贊助標示：**字幕與說明欄未見付費贊助揭露；說明欄含作者 Patreon 文章與提示詞模板的自我推廣。

**快速摘要**

作者把 Google 五天 AI Agents Vibe Coding 課程 Day 4、5 收斂為三件事：先用 spec 說清楚，再以 sandbox／人工批准／依賴管制限制爆炸半徑，最後用 trace 與 eval 驗證是否真的達標。核心不是「讓 AI 寫更多 code」，而是把人的精力移到意圖、邊界與驗收。

**內容重點與重要段落**

1. **01:41｜Spec-driven development：**規格至少交代 what、why、工具／版本、不可碰範圍與 definition of done；用 Given／When／Then 補好壞案例。作者建議先讓 AI 反問缺漏，再進入計畫。
2. **06:00｜三層安全邊界：**sandbox 隔離、重要動作人工批准、dependency allowlist／版本鎖定／CI 掃描。外部 skill、MCP 與套件都先視為不受信任供應鏈。
3. **08:24｜Observability 與 evaluation：**留下 task、step、tool、參數、成本與拒絕原因；傳統 test 驗 deterministic 行為，eval 補 probabilistic 品質，並防 agent 刪測試或用 mock 假裝通過。
4. **11:19｜四個驗收招式：**每一步拿原始需求檢查 drift、看真正輸出／UI 而非只看 source、觀察多輪是否收斂、把人的修正與負評回寫成下一輪 spec／規則。
5. **13:48｜Review 成為瓶頸：**巨大 diff 會讓人快速疲乏；較實用的做法是小批次批准，並在架構先獲同意、測試通過後才給 conditional LGTM。

**可照做的工作流程**

1. 寫 10 行任務 spec：目標、原因、允許工具、禁止區域、完成定義，各列一個正例與反例。
2. 先要求 agent 只產生 plan 與風險清單；人在這一關批准架構與依賴。
3. 在 sandbox 執行；網路、secret、production、付款與刪除動作另設 approval gate。
4. 保存 tool trace、成本與產物；用固定 test 加一個「是否忠於原始需求」eval。
5. 只審查小 diff；把每次退回原因加入 regression set，下一輪重跑。

**涉及工具／模型／功能**

- Google AI Agents Vibe Coding 課程、ADK 2.0、Antigravity、agents-cli。
- Markdown／YAML spec、sandbox、human-in-the-loop approval、dependency pinning、pre-commit／execution hooks、CI、安全測試、trace 與 eval。
- Google 官方課程頁確實把 agent quality、security、memory／context 與 production observability 列為主題；官方 secure agentic coding codelab 也使用 CONTEXT.md、安全測試、STRIDE 與 hooks。[官方課程頁](https://developers.google.com/profile/badges/events/cloud/five-day-ai-agents/award)｜[Google 官方介紹](https://blog.google/innovation-and-ai/technology/developers-tools/kaggle-genai-intensive-course-vibe-coding-june-2026/)｜[安全 codelab](https://codelabs.developers.google.com/secure-agentic-coding?hl=en)

**作者心得、優缺點與限制**

- **作者觀點：**AI 開發的瓶頸已由產生程式碼移到人類 review；信任來自 spec、邊界與驗收，不是模型「看起來很聰明」。
- **優點：**結構清楚，能立即轉成團隊 checklist；把安全、eval 與 review 負擔連成一條 production workflow。
- **限制：**不是逐步操作畫面；片中轉述的個別事故、格式提升比例與 reviewer burnout 數字，未在公開官方課程概覽中逐項找到可核來源，應視為作者／課程轉述，不當成已確認統計。
- **適合對象：**已用 coding agent、準備把 agent 接進 repo／CI／內部工具的工程師與技術主管。
- **是否值得看完整影片：**值得。若時間有限，優先看 01:41–13:48；重點是建立可審核流程，不是學某個 prompt。
- **立即嘗試：**挑一個 30 分鐘內能完成的小 bug，先寫 10 行 spec，鎖住網路與 production 權限，要求 agent 在每步回報「原始需求、目前證據、下一步」，完成後只審 diff 與真實輸出。

## 6. 今天值得嘗試

### 做一份 30 分鐘的「Agent 信任包」

1. **Spec：**目標、非目標、可用工具、禁止範圍、完成條件。
2. **Boundary：**sandbox 執行；secret、網路、刪除、部署都需批准。
3. **Trace：**記錄每次 tool call、參數、成本、拒絕與重試。
4. **Eval：**除既有測試，再加「是否忠於原需求」「是否碰禁止區」「是否真的產生可用輸出」三題。
5. **Compare：**若要試 Qwen3.8 preview，與現用模型跑完全相同的 harness、budget 與 verifier；保存結果，等權重釋出後原樣重跑。
