## 1. 今日最重要的 4 件事

### 1) GitHub Spark 停止收新用戶；既有使用者須在 8/31 前匯出原始碼

- **發布日期：2026-08-04**
- GitHub Spark 已停止接受新用戶與建立新 app；既有使用者可使用至 **2026-08-31**，已部署的 app 會繼續運作，但之後若要再編輯，應先在 Spark workbench 以 `Create repository` 匯出程式碼。[GitHub 官方公告](https://github.blog/changelog/2026-08-04-upcoming-deprecation-of-github-spark-on-github-com/)
- 更急迫的相依性是 `llm()`：其底層 GitHub Models 已於 7/30 退場，因此相關呼叫現在已不能運作。使用者須搜尋 app 程式碼中的 `llm()`，改接自己的 inference provider、API key 與帳務；沒有 `llm()` 的 app 不受這一點影響。
- **實務判斷：**這不是所有「Spark」產品的通用結論，而是 github.com 上的 GitHub Spark 體驗退場。已部署 app 可跑，不代表 AI 功能仍可跑；應把「部署狀態」與「模型相依性」分開盤點。

### 2) Copilot cloud agent 新增 comment 觸發 automation 與每次任務的 reasoning level

- **發布日期：2026-08-03**
- Copilot automation 現在可在 issue 或 pull request 新增指定文字的 comment 時啟動，官方例子包括產生文件、調查 error log、建立技術債 follow-up issue。設定入口在 repository 的 **Agents → Automations**；Business／Enterprise 還需要管理員啟用 cloud agent policy。[comment 觸發官方公告](https://github.blog/changelog/2026-08-03-trigger-copilot-automations-with-comments/)
- 同日，建立 cloud-agent 任務時可為支援的模型選 reasoning level。較高推理層級可能改善複雜任務，但會用更多 token 與 AI credits；這是**每次 run 的成本／品質旋鈕**，不是免費升級。[reasoning level 官方公告](https://github.blog/changelog/2026-08-03-customize-the-reasoning-level-for-copilot-cloud-agent/)
- **限制：**官方公告只確認主 cloud-agent run 的設定，沒有宣稱 Auto model selection 會自動挑 reasoning level，也沒有說 sub-agent 可逐一指定。因此不應把它外推成整個 Copilot agent hierarchy 都已可控。

### 3) 320 萬使用者的 Copilot traces 顯示：agent workload 與聊天服務很不一樣

- **提交日期：2026-07-30；arXiv 於 2026-08-04 新列表露出**
- Microsoft 研究者分析 2026 年 6 月抽樣的 GitHub Copilot production traces，涵蓋 **320 萬使用者、1,300 萬 sessions、7.61 億次 LLM calls、95T tokens**。[論文](https://arxiv.org/abs/2608.00101)
- 作者報告：同一 turn 內 KV-cache hit rate 平均約 90%，跨 turn 降至 55%；換模型或 context compaction 會大幅破壞 cache。使用者在 turn 邊界常閒置數分鐘，作者的輕量 predictor 可捕捉 86–90% 總閒置時間。
- 這些是**作者對抽樣 traces 的系統研究結果**，不是所有 coding agent 的普遍定律。但它提供很具體的 infra 訊號：容量規劃不能只看 token/s；turn 邊界、工具往返、cache 生命周期與人類等待都要納入。

### 4) AgentStream：自我改進 agent 在混合任務流裡不一定愈跑愈好

- **提交日期：2026-07-31；arXiv 於 2026-08-04 新列表露出**
- AgentStream 把 agentic benchmarks 排成 Isolated、Sequential、Interleaved 三類 task stream，組合測試 5 種 self-evolving 方法與 3 個前沿基礎模型。[論文](https://arxiv.org/abs/2608.00155)
- 作者發現 self-evolution 的收益會隨模型能力與 task-stream 組成改變，而且對模型強度不是單調增加；沒有一種方法在各模型、各場景都穩定勝出。
- **實務判斷：**只在獨立任務上驗證「記憶／反思有幫助」不夠。真正部署前，要用接近 production 的交錯任務順序測 contamination、負遷移、錯誤記憶重用與恢復能力。

## 2. 新模型與產品更新

### 今日沒有需要硬湊的新前沿模型發布

- 截稿前未找到比昨日 Qwen3.8-Max／GPT-Live 更值得續報、且有新一手證據的前沿模型發布；因此本節聚焦實際會影響工作流與成本的產品變更。

### GitHub Spark：請做兩層遷移清單

1. **可維護性：**8/31 前把每個需保留的 Spark app 匯出到 repository。
2. **AI runtime：**搜尋 `llm()`；若存在，改接模型供應商並補 API-key storage、spending cap、rate-limit、error handling 與資料政策。
3. **驗收：**分別測「非 AI 頁面仍可用」與「AI 路徑真的能推理」，不要只看部署 URL 還活著。

### Copilot automation：comment 已成為事件入口，但 trigger text 仍應視為外部輸入

- comment trigger 很適合低風險的文件更新、log 初步分析與 follow-up issue 草稿；涉及寫 code、改 PR、存取 secret 或建立大量 issue 時，仍要保留權限邊界與人工批准。
- reasoning level 應按任務選：格式化／分類用低成本設定，架構、除錯、跨檔修改再提高；同一 regression set 記錄完成率、credits 與 elapsed time，避免只憑主觀「感覺更聰明」。

### Copilot 企業治理新增 team specialization

- **發布日期：2026-08-03**
- Enterprise 管理員可在 `managed-settings.json` 將個別 key 標成可由 team 覆寫，再用 `team-mappings.json` 把 team settings file 對應到團隊；沒標成 overridable 的 key 仍由企業層鎖定。[GitHub 官方公告](https://github.blog/changelog/2026-08-03-enterprise-team-specialization-for-managed-settings/)
- `enabledPlugins` 與 `extraKnownMarketplaces` 採 additive 合併；使用者同屬多 team 時，team 層以每個 key 的**較寬鬆值**合併，再置於 enterprise baseline 之下。治理團隊要特別測多重 team membership，不能只驗單一團隊情境。

## 3. 新技術、新方法

### Agent-native serving：把 turn 邊界視為一等資源事件

- **依據：2026-07-30｜Agentic Coding in the Wild**
- 可操作做法：將 `turn_id`、model switch、compaction、tool-call latency、cache hit／eviction 與 user idle 分開觀測；在長 idle 前縮減昂貴資源，在同一 agent loop 內則盡量維持 prefix／cache 穩定。
- 不要從單篇 trace 研究直接抄 90%／55% 當自己的容量參數；先在自家 harness 量同一組事件，再判斷 batching、cache pinning 與 prewarming 是否值得。

### Self-evolving agent：評測單位應是 task stream，不是單題平均分

- **依據：2026-07-31｜AgentStream**
- 至少建立三組 replay：單一 domain 連續任務、跨 domain 交錯任務、刻意插入會誘發錯誤記憶的 adversarial 任務；每輪記錄當前任務品質、後續任務污染、記憶命中與 rollback 成功率。
- 要把「agent 有記憶」和「agent 能可靠選擇何時不用記憶」分開驗收；後者常是 production 的真正難點。

### Graph engineering：有用的核心是顯式 workflow，不是新名詞

- 今日 YouTube 精選把它定義為：以 jobs、edges 與 shared state 拆開 planner、parallel workers、checker、merge 與 human gate。這與 LangGraph 官方的 state／nodes／edges，以及 AutoGen GraphFlow 的 sequential、parallel、conditional、loop 結構一致。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)｜[AutoGen GraphFlow](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/graph-flow.html)
- 但「knowledge graph」與「agent graph」不能混為一談。Microsoft GraphRAG 是以文字抽取、network analysis、LLM prompting／summarization 理解資料關係；agent graph 則控制工作如何流動。[Microsoft GraphRAG](https://www.microsoft.com/en-us/research/project/graphrag/overview/)

## 5. YouTube 深度整理

本次主動檢查 PAPAYA 電腦教室，以及 Greg Isenberg、Better Stack、Tech With Tim、freeCodeCamp 等中英文 AI／coding／agent 頻道。PAPAYA 近 24–48 小時沒有新的合格公開深度片；freeCodeCamp 最新 AI 課程為會員限定；其他候選若重複既有主題、偏一般程式學習或解析深度較低即排除。最後精選 1 部，不為湊數加入第二部。

### Greg Isenberg｜《Why Graph Engineering will 10x your Claude/Codex》

- **發布日期：**2026-08-03
- **查核時數據：**42,210 次觀看；26:28；公開影片（2026-08-05 08:06 CST）
- **連結：**[YouTube](https://www.youtube.com/watch?v=JWhICz1QR8M)
- **字幕：**已完整閱讀 `en-orig` 自動英文字幕。
- **贊助標示：**影片與說明欄未見付費贊助揭露；說明欄含作者 Idea Browser、Late Checkout Agency、The Vibe Marketer 等自家服務導流。

**快速摘要**

作者把「graph engineering」拆成 jobs、arrows、state：先由 planner 分解任務，讓互不相依的研究並行，再由獨立 checker 挑錯、merge 整合，最後在人類批准點停止。最實用的觀點是先手動畫最小 graph、實跑三次，確認真的改善品質後才導入 LangGraph、AutoGen GraphFlow、n8n 等工具。

**內容重點與重要段落**

1. **01:24｜三種 engineering：**prompt engineering 改善提問，context engineering 改善資訊，graph engineering 則設計 AI 周邊的工作流，避免所有步驟擠在一個巨型 chat。
2. **03:35｜jobs、arrows、state：**每個 job 是節點、arrow 是依賴關係、state 是流程目前知道的共享資訊；可同時表達順序與平行工作。
3. **06:44｜knowledge graph vs agent graph：**前者連接資料關係，後者控制 planner、researcher、checker、synthesizer 與 human 的工作移動。
4. **10:01｜diamond pattern：**以 Shopify bookkeeping idea 為例，planner 後分成 customer pain、competitor、distribution 三路，再經 skeptic、merge、human gate。
5. **13:22｜先手動再自動：**先用 Excalidraw／tldraw 畫最小流程並跑幾次；若手動版本沒有產生更好結果，自動化只會更快製造普通結果。
6. **15:10｜三層實作：**白板＋獨立 lanes；Claude Code／Codex 在 repo 內以檔案留下 paper trail；最後才用 LangGraph、GraphFlow、n8n／Make.com 自動化。
7. **20:42｜避免 oversized graph：**更多 agents 可能只是重複同一錯誤與增加協調成本；目標是能提高品質的最小 graph，並把 human gate 放在錯誤代價變高之前。

**可照做的工作流程**

1. 選一個每週會重複的 AI 任務，只寫一句最終產物。
2. 列出真正需要的 jobs；只在有資料依賴時畫 arrow，無依賴者才平行。
3. 把 producer 與 checker 分開；checker 檢查來源、過期資訊、漏掉的替代方案與過度自信。
4. merge 只整合通過檢查的 evidence，並保留來源與被排除理由。
5. 在寄信、付款、部署、公開發布、改 production 資料前放 human gate。
6. 手動跑三次，刪掉沒有提高品質的節點，再決定是否導入框架。

**涉及工具／模型／功能**

- Claude Code、Codex、LangGraph、AutoGen GraphFlow、n8n、Make.com、Microsoft GraphRAG、Excalidraw／tldraw。
- LangGraph 官方確認 graph 由 state、nodes、edges 組成，並支援 persistence 與 human-in-the-loop；AutoGen GraphFlow 官方確認支援順序、平行、條件分支與具退出條件的 loop，但目前標為**實驗性功能**。[LangGraph 官方文件](https://docs.langchain.com/oss/python/langgraph/overview)｜[AutoGen 官方文件](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/graph-flow.html)

**作者心得、優缺點與限制**

- **作者觀點：**graph engineering 是從「找完美 prompt」轉向「設計可管理 workflow」；最小可用 graph 比龐大多 agent 圖更重要。
- **優點：**概念清楚、有具體 diamond pattern、能套用研究、客服、內容與 coding；特別強調 checker 與 human gate。
- **限制：**片名的「10x」沒有對照實驗或量化 benchmark；Shopify 案例是示意流程，不是 production case study；「不同 agent／checker」也不自動保證錯誤獨立。
- **適合對象：**已反覆用 AI 做研究、內容、客服或 coding，但流程散落在長對話，且難以重現與驗收的人。
- **是否值得看完整影片：**值得看，但把它當 workflow 設計入門，不是效能實證。時間有限可看 01:24–03:35、10:01–16:00、20:42–24:53。
- **立即嘗試：**把一個現有任務畫成 `planner → 3 個平行 evidence jobs → skeptic → merge → human approve`；今天先手動跑，不安裝任何新框架，記錄哪個節點真正改變了決策。

## 6. 今天值得嘗試

### 做一個 30 分鐘「最小可重現 agent graph」

1. **輸入：**固定一個真實 issue、研究問題或客訴，不要用玩具 prompt。
2. **圖：**最多 6 個 jobs；明確寫每個節點的 input、output、stop condition。
3. **證據：**每個 worker 輸出獨立檔案並附來源；checker 不能只回「看起來正確」。
4. **成本：**保存 model、reasoning level、tokens／credits、elapsed time。
5. **安全：**任何 comment-triggered automation 先設成草稿或只讀；要寫入 repo／issue 前再人工批准。
6. **比較：**與單一長 prompt 跑同一題；若品質沒有明顯提高，就刪節點，不急著上 graph framework。
