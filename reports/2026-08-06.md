### 2) 自我改進 agent 可能把「最有自信的錯誤」反覆寫回記憶

- **v1 提交日期：2026-06-29；arXiv cs.AI 新列表：2026-08-05**
- 《Memory Reward Inflation in Self-Improving LLM Agents》把問題稱為 **Echo Gap**：agent 用自己或相近 LLM 的評分替 memory episode 打分，錯誤 episode 可能得到過高 reward；之後即使只按語意相似度檢索，模型也可能因看到較高 utility 標記而更信任它。[論文](https://arxiv.org/abs/2608.00017)
- 作者主張，較強的 LLM judge 不一定能修正問題，關鍵是 verifier 的錯誤要和原本 self-grade bias **去相關**。可用訊號包括執行結果、測試、static analysis、retrieved evidence 或 invariant check，而不只是再請另一個相似模型評一次。
- 在 BIRD text-to-SQL 的作者實驗中，LUCID 把 execution accuracy 提高到 **56.9%**，高於 self-graded memory agent 的 54.0% 與無記憶版本的 52.4%。這仍是作者在單一 end-to-end benchmark 的結果，不是所有 agent memory 的普遍增益。

### 3) RAG-Tester：不要只測回答，要一起測文件、retrieval、embedding 與拒答

- **v1 提交日期：2026-07-26；arXiv cs.AI 新列表：2026-08-05**
- RAG-Tester 自動產生 retrieval documents、queries 與 expected outputs，再跑完整 RAG pipeline，針對複雜段落、答案不存在的 negative query、跨文件覆蓋與 retrieval／generation 交互錯誤設計測試。[論文](https://arxiv.org/abs/2608.00054)｜[重現程式碼](https://github.com/Anje13/GBL_RAGTester)
- 作者在 24 組 LLM／embedding 配置、72,000 次測試中找出 21,633 次失敗；摘要稱比 baseline 多 6.6%，內文 RQ2 則寫 6.22%，應視為約 **6.6%**，不把小數差異過度解讀。
- **限制：**評分仍使用 LLM-as-a-judge，test oracle precision 為 80.6%；目前聚焦 PDF，multi-document、multi-hop、adversarial cases 留待未來。它適合當 failure-finding harness，不應被當成 correctness proof。

### 4) Bazaar 顯示：agent 會搶到客戶，不代表會賺錢，也不代表需求改變後會改觀

- **v1 提交日期：2026-07-30；arXiv cs.AI 新列表：2026-08-05**
- Visa Research 的 Bazaar 讓 LLM merchant 在隱藏偏好、競爭對手、稀疏 win／loss feedback 與中途需求 shock 下，反覆選產品組合與定價；封閉形式的 customer utility 讓 profit、regret 與 adaptation 能精確計算。[論文](https://arxiv.org/abs/2608.00102)
- 11 個模型中，Gemini 3.1 Pro 的 win rate 領先、shock 後恢復最快；Opus 4.6 adaptive xhigh 的 profit 領先。profit 與每次勝出的 margin 關聯高於單純 win rate，而即使最佳 agent 也只取得不到 hindsight-optimal profit 的三分之一。
- **限制：**顧客是人工 archetype、每場只有一個 LLM 對三個相同 bots，且只有一次大型 shock。這是受控的 pricing-skill probe，不是實際市場營收預測，也不能直接用來支持個人化差別定價。

## 3. 新技術、新方法

### Agent memory：把 reward source 和 memory content 一起保存

- **依據：2026-06-29｜Echo Gap／LUCID**
- 每筆 memory 除了 task、answer、score，至少保存 scorer model/version、score reason、外部 evidence、test／execution result、寫入時間與 reuse count。
- retrieval ranking、提示中顯示的 confidence／utility、以及實際採用率要分開觀測；只看「被取回幾次」會漏掉 similarity-only retrieval 下的 trust amplification。
- 高風險 memory 不以另一個同類 LLM 的同意作唯一放行條件；優先接可執行測試、資料庫查詢結果、schema／policy validator 或獨立 retrieval evidence。

### RAG：用 coverage-oriented test generation 取代幾題 happy path

- **依據：2026-07-26｜RAG-Tester**
- 最小測試矩陣應包含：答案存在、答案不存在必須拒答、跨多段才能回答、retriever 找到但 generator 沒完整使用、複雜句法、相似但不支持答案的 hard negative。
- failure label 要分成 retrieval miss、rerank miss、context truncation、unsupported generation 與 judge uncertainty；否則換 embedding 或 prompt 時無法知道修到哪一層。
- LLM judge 本身也要抽樣人工複核，並保存 judge prompt／model/version；80.6% precision 提醒我們，測試 oracle 也會製造 false positive。

### Dynamic agent eval：在環境改變後測「放棄舊信念」

- **依據：2026-07-30｜Bazaar**
- 在 pricing 之外也可套用：先讓 agent 在穩定規則下學會策略，再無預警更換 API contract、客戶偏好或工具可靠度，量測 detection lag、recovery time、regret 與 rollback 行為。
- 靜態 benchmark 只會看到最終平均分；production 更需要知道 agent 何時把新證據誤判成 anomaly，以及舊 memory／strategy 會黏多久。

## 6. 今天值得嘗試

### 做一個 45 分鐘「記憶與 RAG 雙重污染測試」

1. 準備 10 個有明確答案的 query，其中 2 個放入相似但錯誤的 document／memory。
2. 讓 agent 為每個回答 self-grade，保存 score、reason、retrieved evidence 與 reuse count。
3. 第二輪加入相似 query，觀察高分錯誤是否更常被採用，並區分「被檢索」與「被信任」。
4. 加入一個不同 failure mode 的 verifier：可執行測試、DB query、schema check 或獨立 evidence retrieval，不用另一個只看文字的同類 judge。
5. 比較 correction 前後 accuracy、false reject、latency 與成本；任何自動 memory write 先保留 quarantine／rollback。
