### 4) Programmatic tool calling：把工具暴露成 typed code，14 個模型中有 11 個不輸 JSON calling

- **發布日期：2026-08-06（arXiv），2026-08-07 列入近期更新。**《The Bitter Lesson of Tool Calling》在 BFCL v4 比較 14 個模型：把工具包成 typed Python stubs、由模型用程式串接／平行呼叫的 PTC，在 11／14 模型匹配或超過原生 JSON tool calling；作者報告 GPT-5.6 家族相對基線提升 10.6%。[論文](https://arxiv.org/abs/2608.06370)
- 在 parallel fan-out 條件下，PTC 於 13／14 模型不低於基線；context rot 測試中 PTC 維持穩定，而 JSON 基線平均下降 2.3%。
- 這不代表「code 永遠比 JSON 好」。結果來自作者在 BFCL v4 的實驗，執行器、型別 stub、sandbox、錯誤處理與模型是否擅長寫 code 都是 harness 的一部分；上 production 前仍需以自己的工具 schema、延遲與副作用重測。

### 5) CodeGrep 與 TRAJDEBUG：Coding Agent 的下一個瓶頸是找對檔案與找出最早關鍵錯誤

- **發布日期：2026-08-06。** CodeGrep 是 14B retrieval agent，以 GRPO 學會多回合、平行使用 grep／glob／read，再把候選檔交給固定的 coding agent。作者在 500 個 SWE-Bench Verified 任務報告：resolve rate 27.0%（無 retrieval 基線 25.8%），已解任務少 15% rounds、少 19% tokens。[CodeGrep 論文](https://arxiv.org/abs/2608.05886)
- 同日的 TRAJDEBUG 不只標局部錯誤，而是追蹤錯誤何時出現、是否被後續修復、是否仍造成終局失敗；作者建立 486 條人工標註的 Tau2Bench／SWE-Bench Pro 失敗軌跡。[TRAJDEBUG 論文](https://arxiv.org/abs/2608.06346)
- 兩篇共同提醒：降低 token 不能只靠縮短 prompt；應把「repository 探索」與「失敗歸因」各自做成可量測元件。**限制：**兩者都是作者 benchmark 結果，CodeGrep 的 downstream agent／模型設定與 TRAJDEBUG 的人工標註規則都會影響數字，尚待獨立重現。

## 3. 新技術、新方法

### 把 tool calling 當可替換的 execution language

依《The Bitter Lesson of Tool Calling》，可在 staging 同時保留 JSON 與 programmatic 兩種 adapter：相同任務、相同模型、相同工具權限，分別量成功率、invalid call、總 turns、parallel fan-out、latency 與副作用攔截率。PTC 的價值不是「讓模型任意寫 Python」，而是用受限、typed、可審計的程式表達複合呼叫；執行仍應在 sandbox，並對網路、檔案與 credentials 設硬邊界。

### 歷史紀錄不是權威狀態

- **發布日期：2026-08-06。**《When History Lies》測試結構仍合法、語意看似合理、但已不適用目前請求的歷史軌跡。作者在 Qwen3-1.7B 上發現，污染歷史會翻轉 32.1% 原本正確的決策，常見錯誤是沿用已污染的 entity 或 interface convention。[論文](https://arxiv.org/abs/2608.06057)
- 作者提出以 oracle-state teacher 教只看到 polluted history 的 student；在該設定下 Balanced Tool-Use Accuracy 達 87.0%，高於 Gold-SFT 的 66.3%。這是特定模型／benchmark 的作者結果，不是普遍保證。
- 實務做法：把「最新使用者要求、目前工具 schema、外部系統實際狀態」放在高優先區；對 conversation history 的 account ID、路徑、日期與 tool signature 加 freshness／provenance，執行前重新讀取權威狀態。

### 評 harness，不只評 model

- **發布日期：2026-08-06。** HarnessOpt-Bench 把 prompt、tools、control flow、memory 與 orchestration code 一起視為可優化 harness；在 4 個 downstream tasks、5 個 frontier LLM、111 次計分 run 中，作者發現 optimizer model 間的差異大於其操作的 coding harness，native harness 也沒有一致勝出。[HarnessOpt-Bench](https://arxiv.org/abs/2608.06301)
- 測試用 trusted execution environment 隔離 held-out test、限制 target-agent resource，並保留每個候選版本供稽核。這種「固定 evaluation budget＋不可偷看 test＋版本化候選」比讓 Agent 自評 prompt 改進更接近可信的 harness optimization。

## 4. 社群實戰心得

### Worktree 受歡迎，但「哪個 clone 才是工作來源」仍要顯式處理

- **討論更新日期：2026-08-06。** 一則 GitHub Copilot app 使用者討論中，有人把 worktree-based task 切換列為明顯的生產力提升；同一串也有人追問：同一 repository 有四個本機 clone 時，app 能否像 CLI `/cwd` 一樣指定來源 clone。[Reddit 討論](https://www.reddit.com/r/GithubCopilot/comments/1v9gpsp/i_love_the_new_github_copilot_app/)
- 這是小樣本第一手心得，不是效能研究。它指出一個真實操作風險：worktree 解決「同一來源樹的並行隔離」，但不自動解決多 clone 的環境差異、未追蹤檔案、不同 credentials 或不同 base commit。
- 今日可採用的做法：每次開 Agent 前記錄 repository absolute path、`git rev-parse HEAD`、dirty status 與 worktree path；完成後用 diff／測試驗證，而不是只看 app 中的 task 名稱。

### Tool calling 壞掉時，先查 harness 與 parser，再怪模型

- **實戰討論日期：2026-07-29（略超過一週，作為方法補充）。** 一位本地 Agent 開發者把每個工具的 JSON Schema 編成 GBNF，並在每輪先用 semantic router 把約 50 個工具縮到少數候選，目標是阻止小模型產生 code fence、錯誤 tool name、缺 key 或 trailing prose。[Reddit 技術整理](https://www.reddit.com/r/LocalLLaMA/comments/1v9qvn3/i_built_a_gbnf_grammar_compiler_that_makes_8b/)
- 這與今日 PTC 論文不是同一結論：前者強化 JSON 的格式與候選約束；後者改用 typed code 表達工具組合。兩者都說明 model score 之外，schema、parser、router、execution boundary 會實際決定可靠性。
- 社群文章未提供可比的獨立 benchmark，應把做法視為可測假設；最小測試是建立 20–50 個 golden tool calls，對每次模型／量化／parser／prompt 升級做 regression。

## 6. 今天值得嘗試

### 45 分鐘：替 Agent 做「fresh state＋隔離 worktree＋雙 tool adapter」小測試

1. 選 10 個會讀檔、搜尋與呼叫一個低風險工具的真實任務；固定模型與評分規則。
2. 每個任務在獨立 worktree 執行，開跑前記錄 absolute path、HEAD、dirty status；不放真實 credentials。
3. 準備一段看似合理但過期的 conversation history，要求 Agent 在執行前重新讀取權威檔案／API state；記錄是否仍沿用舊 entity 或舊 schema。
4. 同一批任務各跑 JSON tool calling 與受限 typed programmatic calling；比較成功率、invalid calls、turns、tokens、latency 與 canary／副作用攔截。
5. 失敗時標出「最早仍影響終局的錯誤」，不要只看最後一條 exception；把結果存成可重跑 regression suite。

這個小測試同時落實今日的 worktree、歷史污染、PTC、CodeGrep 與 TRAJDEBUG 洞見，但不需要先重寫整套 Agent。
