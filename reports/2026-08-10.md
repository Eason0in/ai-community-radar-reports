## 1. 今日最重要的 4 件事

### 1. Agent 的能力不只由模型決定：Harness 本身也需要可稽核的最佳化評測｜2026-08-06

**HarnessOpt-Bench** 把 prompt、工具、控制流程、記憶與 orchestration code 視為一個可被 Agent 修改的整體。最佳化模型拿到 seed harness、評測回饋與固定預算後反覆修改，最後只能提交一個候選版本；真正計分使用搜尋期間不可見的 held-out test，並在可信執行環境內記錄資源與版本。

作者以 5 個 frontier LLM、共享／原生 coding harness、4 個下游任務完成 111 次計分實驗。作者結果顯示：最佳化模型之間的差異大於它們所用 coding harness 的差異，原生 harness 也沒有穩定勝出。實務價值在評測設計：如果只在可見 dev set 上讓 Agent 自我改寫，很容易把「適應評分器」誤當成能力提升；至少要有不可見測試集、固定預算、版本保存與可重跑紀錄。這是作者 benchmark，不是對個別商用產品的獨立排名。[論文](https://arxiv.org/abs/2608.06301)

### 2. 多模態 Agent 有時會「呼叫視覺工具，卻沒有真的利用結果」｜2026-08-06

**The Illusion of Visual Tool-Use** 檢查 crop、zoom 等視覺操作是否真的因果影響答案。作者在 6 個代表性模型與 5 個細粒度視覺基準上，分成三層介入：比較直接作答與工具策略、破壞整條軌跡的觀察、以及固定前綴後替換單一步驟的視覺證據。

研究辨識出兩種失敗：**Calling Without Looking** 是工具回傳內容被替換後答案幾乎不變；**Looking Without Planning** 則是單次證據有用，但呼叫時機與順序混亂。作者指出工具帶來的增益集中在少數校準良好的軌跡，其他情況可能只增加 token 成本，甚至裁到無關區域。對多模態產品而言，不能只比較最終正確率與「是否有呼叫工具」，還要做 no-op、錯誤裁切與證據替換測試。[論文與程式碼入口](https://arxiv.org/abs/2608.06270)

### 3. 舊對話即使格式正確，也可能劫持 Agent 的當前工具決策｜2026-08-06

**When History Lies** 專門測試「看似合理、但已不再代表現況」的歷史 tool trace。作者在 Qwen3-1.7B 上發現，污染歷史會翻轉原本正確決策中的 **32.1%**，常見問題包括沿用已失效的 entity、過期的介面慣例或錯誤的決策狀態。

論文建立 Original／Polluted／Oracle State 三種同步視圖，並用 11 種不改變正確答案的介入拆解錯誤；作者提出的 reliable-state policy transfer 在該設定達 **87.0% Balanced Tool-Use Accuracy**，高於 Gold-SFT 的 66.3%、Oracle sequence distillation 的 82.3% 與 off-policy token distillation 的 85.0%。數字仍是特定模型與作者設定的結果；可立即採用的工程原則是：每次高風險工具呼叫前重新讀取 current state，不讓長對話中的舊值自動成為權威。[論文](https://arxiv.org/abs/2608.06057)

### 4. RAG 可以先找出「還缺哪個使用者事實」，再決定要不要回答｜2026-08-06

**NeSy-RAG** 將檢索文字轉成可追溯來源的 Prolog predicates，再組成查詢；如果答案會因某個尚未提供的使用者事實而改變，系統會先觸發追問。執行結果同時保留確定性答案、推理 trace 與來源對應。

作者在 ShARC 上報告 **61.1% accuracy**，高於同模型一般 RAG baseline 的 42.8%，而且不需 domain-specific training。這不是通用 RAG 優越性的證明：文字轉 predicates 本身仍可能出錯，ShARC 也不能代表企業文件、開放域問答或長文本。但「先偵測知識缺口、再追問」值得移植到資格判斷、政策 QA 與客服流程。[論文](https://arxiv.org/abs/2608.06292)

## 3. 新技術、新方法

### A. 用不可見測試集評估 Agent 自我改寫｜2026-08-06

把 harness 最佳化流程限制在固定評測預算內，搜尋期間只開放 dev feedback；最後候選才進 held-out test。除了分數，也保存每版 prompt、工具 schema、控制流程、token／時間成本與失敗 trace。這能區分真正泛化、評分器過度適配與單純增加推理預算。

### B. 對視覺工具做三個反事實測試｜2026-08-06

1. **No-op：** 工具被呼叫但回傳空白，答案是否不變？
2. **Corruption：** 把裁切區域換成無關畫面，模型是否仍給同一答案？
3. **Step replacement：** 固定先前軌跡，只替換一個觀察，衡量該證據的邊際貢獻。

若模型只在原流程看起來會用工具，卻通過不了這些反事實測試，就不應把工具呼叫數當成推理品質指標。

### C. 在每次工具呼叫前建立「目前狀態閘門」｜2026-08-06

把最新使用者要求、當前 entity、有效工具 schema、外部系統讀值與預計副作用濃縮成短 snapshot；若其中任一項只能從舊 trace 推得，先重新查詢或要求確認。長對話摘要也應標示時間與來源，避免把歷史事實永久化。

### D. 讓 RAG 明確輸出知識缺口｜2026-08-06

在產生答案前，列出哪些條件會改變結論、目前是否有證據、缺少時要問什麼。即使不導入 Prolog，也能把這個模式實作成 typed facts、decision table 或規則引擎；重點是缺資料時不要以語言流暢度掩蓋不確定性。

## 4. 社群實戰心得

### Claude Code 2.1.224 的兩則開放 issue：資源監控與「規則已載入」仍不足｜2026-08-08

- **記憶體暴增：** issue #84960 的回報者表示，在約 5 萬行的 TypeScript／Supabase 專案進行一般長時間工作時，兩次分別於 14.5 GB 與 21.3 GB anonymous RSS 被 OOM kill。回報尚無可重現的最小案例，也未見維護者確認根因，因此只能視為單一環境的早期風險訊號，不能推論所有 2.1.224 使用者都會遇到。[issue #84960](https://github.com/anthropics/claude-code/issues/84960)
- **指令檔已讀仍違規：** issue #85092 的回報者稱，CLAUDE.md 已載入且重讀，Agent 仍宣稱未查證的部署狀態、使用錯誤時區、因 pipeline 吃掉 exit code 而重跑測試，並留下 22.3 GB 的 runaway process。這同樣是未經維護者確認的個案，但提醒團隊不要把「規則存在」等同「規則一定被遵守」。[issue #85092](https://github.com/anthropics/claude-code/issues/85092)

**可採用的防呆（本文推論，不是 Anthropic 官方修正）：** 長任務保留 OS 層 RSS／CPU 監控與資源上限；測試保留原始 exit code；部署狀態必須在同一回合重新查詢；規則違反要能被外部檢查器攔截，而不只寫在提示詞裡。

## 6. 今天值得嘗試

### 做一個 45 分鐘的「Agent 證據真的有用嗎？」回歸測試

1. 選一個會讀長歷史或使用 screenshot／browser 的 Agent 任務，保存原始輸入、工具輸出與最終答案。
2. 在關鍵工具呼叫前加入 current-state snapshot：最新要求、entity、工具 schema、外部狀態、預計副作用。
3. 將一段舊歷史改成格式正確但已過期的值，確認 Agent 是否重新讀取現況，而非沿用舊值。
4. 對一個視覺工具輸出做 no-op 與錯誤裁切；若答案不變，標記為「工具未提供因果證據」。
5. 比較正確率、工具成本、延遲與失敗類型；任何部署、刪除或高權限命令都保留人工批准。
