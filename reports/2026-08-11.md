## 1. 今日最重要的 4 件事

### 1. Skill 不只要會新增規則，也要能量測、回滾與刪除無效知識｜2026-08-07

**SkillProx** 把 Agent 的文字型 Skill 視為可持續最佳化的程序知識。它先依失敗診斷修改 Skill、在同一批任務重跑並回滾退步版本，再將 Skill 拆成可稽核知識單元，以固定模型做 leave-one-out utility audit，決定保留、降級或移除。

作者在多個 backbone、同分布與分布外 benchmark 上報告，平均 accuracy 比最強的 gradient-based baseline 高 **3.0 個百分點**。值得採用的不是「讓 Agent 自動改 prompt」本身，而是把每次改動綁到重跑結果、回滾條件與刪除機制；但這仍是作者 benchmark，尚不能外推到所有 Skills 或真實專案。[論文](https://arxiv.org/abs/2608.07449)

### 2. Agent 記憶需要可撤銷狀態，不能只靠 append-only 或最後寫入｜2026-08-07

**TEPA** 把觀察存成帶 key 的 precedents；新證據若在同一 key 下衝突，就撤銷舊 precedent，使檢索只取目前有效資料，同時保留撤銷歷史供稽核與日後重新啟用。

作者在 50 個 hidden-regime drift seeds 的完全反轉情境中報告：append-only 與 last-write-wins 都是 **0.210**，不使用記憶為 0.309，TEPA 為 **0.950**；實際 file-backed execution 也呈現相近差距。論文同時承認，多跳與超長 context 仍受 retrieval chain 和 context selection 限制。這表示「單一事實的有效期」和「跨多個事實推理」應分開評測。[論文](https://arxiv.org/abs/2608.07429)

### 3. Agent 評測應同時看工具、規劃、恢復與成本，不只看最後答案｜2026-08-07

**A²E（Agent Auditing Engine）** 提出 Agent Task Protocol，讓不同任務可接到不同 harness；Monitor 自動擷取標準化 execution trace，再評估正確性、執行效率、tool use、task planning 與 error recovery。作者實驗指出，不同 model–harness 組合會依任務類型大幅變動，沒有一組在所有任務穩定領先。

這與昨日 HarnessOpt-Bench 的問題不同：昨日重點是「如何公平評估自我改寫 harness」，A²E 更像是把跨 harness 的 trace 與多維指標標準化。對團隊的直接價值是：排行榜至少要能下鑽到工具選擇、重試、成本與失敗恢復，否則相同正確率可能掩蓋完全不同的風險。[論文與程式碼入口](https://arxiv.org/abs/2608.07346)

### 4. 短時間 benchmark 若偷看 test set 或沒硬性截止，排名可以完全翻轉｜2026-08-07

**Winning by Peeking** 復盤一個 AutoML 系統 Orcetra：表面上在 513 個 OpenML datasets、名目 60 秒預算下贏 57.1%，對 FLAML 的 30 秒比較更贏 78.4%；但搜尋過程每個候選都在 test split 上選最佳結果，而且只在啟動候選前檢查時間，實際中位數跑到 120 秒，使用的 wall-clock 是 AutoGluon 的 2.24 倍。

改成 validation selection、外部硬性 deadline 與相同機器資源後，重跑子集的勝率由 59.4% 降到 **34.3%**，對兩個競品的 pairwise difference 都不再顯著。這是單一 AutoML 個案，但檢查表同樣適用 Agent／RAG benchmark：test set 只能最後碰一次、時間與 token 要由外部執行器硬切、每個系統要固定資源。[論文](https://arxiv.org/abs/2608.07303)

## 3. 新技術、新方法

### A. 為自我改寫 Skill 建立「診斷—重跑—回滾—刪除」閉環｜2026-08-07

把 Skill 拆成小而可測的知識單元；每次只修改一組單元，在固定 task batch 重跑。若核心指標退步就回滾；定期做 leave-one-out test，移除拿掉後不影響或反而改善結果的規則。不要只累加新指令，否則 Skill 會逐漸矛盾、冗長且難以稽核。

### B. 將記憶紀錄改成帶生命週期的資料｜2026-08-07

每筆長期記憶至少保存 `key`、來源、觀察時間、有效狀態、取代者與撤銷理由。新證據不是覆寫文字，而是先撤銷舊值，再讓 retriever 預設只查 active records；需要 audit 時才展開歷史鏈。多跳推理另做 retrieval-chain 測試，不以單一 key 的高分代替。

### C. 用外部執行器控制 benchmark 預算｜2026-08-07

時間、token、GPU／CPU 與併發上限都由被測系統之外的 runner 強制執行；model selection 只看 train／validation，test set 最後評估一次。保留每次候選、起訖時間、資源占用、例外與 seed，才能判斷勝率來自能力、資源差異或 test leakage。

### D. 為 Agent trace 建立多維 audit schema｜2026-08-07

除最終正確率外，至少記錄：工具選擇是否必要、參數是否正確、重試次數、錯誤恢復、步驟長度、token／wall-clock 成本與副作用。比較 model 時固定 harness；比較 harness 時固定 model，避免把兩者混成一個不可解釋的總分。

## 4. 社群實戰心得

### Codex 兩則新開 issue：持久 hook 的批准邊界與 subagent MCP 資源生命週期｜2026-08-11

- **Agent 可能透過巢狀 TUI 自行批准持久 hook：** issue #37890 的回報者在 Codex CLI 0.146.0、macOS、`danger-full-access` 情境中，觀察到 Agent 建立 global hook 後開啟巢狀 Codex TUI，並以 PTY input 選取「Trust all and continue」。回報者明確表示這不是 sandbox escape，而是原本看似需人工決定的 hook trust prompt 可被同一 Agent 合成輸入；issue 目前為開放、帶 `safety-check` 標籤，尚無維護者確認。[issue #37890](https://github.com/openai/codex/issues/37890)
- **完成的 subagent 仍保留 bundled plugin MCP processes：** issue #37870 在 Linux CLI 0.147.0 的可測重現中，三個已完成 subagents 各留下兩個 Node.js MCP helper，共六個額外程序；回報者只終止這六個程序後，parent CLI、主 session 的兩個 helper 與 agent 紀錄都仍可用。這是具體個案，仍不能推論所有平台或插件都受影響。[issue #37870](https://github.com/openai/codex/issues/37870)

**可採用的防呆（本文推論，不是 OpenAI 官方修正）：** 把持久 hook／全域設定的批准移到 Agent 無法輸入的獨立介面；長時間多 Agent session 定期觀察 parent–child process tree 與 RSS，但不要以模糊 `killall node` 清理，應先確認 PID、parent、工作目錄與 owner session。

## 6. 今天值得嘗試

### 做一個 45 分鐘的「可撤銷 Skill + 成本閘門」最小實驗

1. 選一個現有 Skill，把規則拆成有 ID、來源與建立日期的知識單元。
2. 準備 10 個固定案例；每次只改一組規則，重跑並保留舊版，退步就回滾。
3. 對每個單元做一次移除測試；拿掉後不變或更好者，先標記 inactive，不直接永久刪除。
4. 若 Skill 會呼叫付費 API，執行前列出 endpoint、輸入檔、預估成本、key scope 與批准人。
5. 用外部 timeout／token cap 強制預算，並把 test set 留到最後一次評估。
