> 查核時間：2026-08-12 08:05（Asia/Taipei）。本期優先涵蓋最近 24–48 小時，研究以 8 月 11 日 arXiv 新上架清單為主；已與 8 月 11 日報告去重，不重複 SkillProx、TEPA、A²E、短預算 benchmark test leakage 與昨日兩則 Codex issue。

## 1. 今日最重要的 5 件事

### 1. Motif 3 公開完整技術報告，但目前可下載的仍是 Beta、非商用權重｜2026-08-10

Motif Technologies 的 **Motif 3** 是 314B 總參數、每 token 啟用 13.2B 的 decoder-only MoE；每層有 384 個 routed experts、選 8 個，預訓練約 12.5T tokens，原生 context 最長 256K。報告也描述 GDLA、MXFP8、六個 RL specialist teachers、software-engineering teacher 與 on-policy distillation。

需注意「有權重」不等於「可直接商用」：Hugging Face 現有的是中間 Beta checkpoint，權重免申請下載，但授權僅允許個人、教育與非商業研究；模型需 `trust_remote_code=True`，官方 vLLM 範例只測過 B200／H200，且尚無 inference provider。論文 benchmark 是作者結果，不能視為獨立結論。[技術報告](https://arxiv.org/abs/2608.09119)｜[官方模型卡](https://huggingface.co/Motif-Technologies/Motif-3-Beta)

### 2. Frontier model 可自行組合最佳化流程，但較弱 optimizer 仍需要腳手架｜2026-08-10

**Open-Ended Optimization（OEO）** 固定 objective、可用互動、資源預算、資料邊界與 evaluation，卻不預先指定如何蒐證、改寫、選候選與停止。作者以 GPT-5.5 當 optimizer，對上 SkillOpt 與 GEPA，在 14 次 head-to-head 中取得 **12 勝、1 和、1 次落後 0.21 個百分點**，中位數只用 SkillOpt 設定 target-interaction token budget 的 **34.3%**。

這不是「所有 pipeline 都可刪掉」：medium optimizer 仍由 SkillOpt 勝出，weak optimizer 甚至無法操作同一 OEO 介面。相較昨日 SkillProx 強調診斷、回滾與刪除，今天的新訊號是：外部硬限制要保留，但流程細節是否寫死，應依 optimizer 能力做消融測試。[論文](https://arxiv.org/abs/2608.09629)

### 3. 單一 Skill 可藏條件式後門，正常測試幾乎不觸發｜2026-08-10

**ElasticBack** 在 Skill 文件植入規則 `R`，再讓使用者 query 中的 benign-looking trigger `T` 當開關；只有兩者共存才執行惡意 payload。作者先固定規則，再用帶 stealth constraint 的 genetic search 演化 trigger，使後門在一般輸入保持休眠。

作者在三種目標行為、每種 50 個 Skills、四個 Agent LLM 上報告高 attack success、近零 false positive、clean accuracy 維持，且能跨模型轉移與規避受測的 deployment-time defenses；摘要沒有提供所有精確數字，仍需把它視為作者安全研究結果。實務上，Skill 稽核不能只跑正常案例，也要測「文件規則 × 使用者輸入」的組合觸發。[論文](https://arxiv.org/abs/2608.09577)

### 4. Android accessibility tree 可能把環境文字升格成 Agent 指令｜2026-08-09

**Not an A11y** 測試依賴 Android accessibility tree、再輔以 screenshot 的 mobile agents。作者示範隱藏與可見的惡意文字可造成 goal hijacking、context drift 與未授權操作；MobileRun 搭 Gemma4:31B 的整體 attack success rate 為 **0.822**，Mobile-Use 搭 Qwen3.6:35B 降到 **0.150**，但仍未消除漂移與越權。

核心不是單一模型誰較安全，而是架構把 passive UI metadata 當成與使用者命令同等可信。可行方向是把 accessibility／OCR 文字標成 untrusted data、把 action authorization 留在獨立 policy layer，敏感操作再做人類確認。[論文](https://arxiv.org/abs/2608.08939)

### 5. 安全與可靠性開始移到 harness runtime，而不是只改 system prompt｜2026-08-10

兩篇新研究從不同面向補足 runtime control：**SHE** 把 harness 分成 System Prompt、Rule Bank、Safety Memory、Tool Policy，依失敗 trajectory 做責任歸因與局部演化；作者在 Agent-SafetyBench 報告 attack success rate 相對 static SafeHarness 降低 **3.1 倍**，benign utility 同時提升。**SkillSentry** 則把 Skill 規格與成功／失敗 traces 轉成 DSL runtime guidance，逐步監控並修正執行；作者在 15 個 Skills、兩種 Agent harness、四個 backbone 組合上報告平均 task success 提升 **24.1%**、重跑變異更低。

兩者數字都是作者 benchmark；共同價值是把「應該遵守」變成可觀察的 runtime assertion、trace 與阻擋／修正動作。[SHE](https://arxiv.org/abs/2608.09885)｜[SkillSentry](https://arxiv.org/abs/2608.09253)

## 3. 新技術、新方法

### A. 先固定邊界，再決定讓 optimizer 自由到哪裡｜2026-08-10

把 objective、資料 split、可呼叫工具、token／wall-clock budget、成功條件與停止權固定在外部 runner；再做 prescribed pipeline 與 open-ended optimizer 的 A/B。強模型可嘗試動態組合流程，medium／weak model 則保留 staged edits、候選選擇與 rollback，不要把高能力模型的結果外推到所有部署。

### B. Skill 安全測試要加入「雙條件觸發矩陣」｜2026-08-10

除正常案例外，建立 Skill 文件片段 × user query 變體的組合測試；觀察同一 benign query 在 Skill 有無特定規則時，tool call、資料讀取與輸出是否突變。掃描混淆文字仍不夠，還要在 runtime 對敏感工具做 allowlist、參數 schema 與 side-effect assertion。

### C. 將 harness 拆成可歸因、可回滾的安全元件｜2026-08-10

System Prompt、Rule Bank、Safety Memory 與 Tool Policy 各自版本化；一個 failure trace 先定位責任元件，再做局部修改與 safety／utility regression。若只能整份 prompt 一起改，就難判斷是哪條規則改善安全、又是哪條規則破壞正常任務。

### D. GUI grounding 可拆成語意理解與精確定位兩階段｜2026-08-10

另一篇新研究讓 frozen MLLM 先把抽象指令展開成含 layout cues 的描述，再由不做 coordinate regression 的專用 grounding model 匹配 layout candidates。作者在 ScreenSpot-Pro 報告 grounding accuracy 比 end-to-end 系統高逾 20%，Mind2Web 的 success／element selection 高逾 15%；這仍是作者結果，但提供一條減少座標幻覺的可測設計路徑。[論文](https://arxiv.org/abs/2608.09654)

## 4. 社群實戰心得

### Codex VS Code extension 的 project-scoped `approval_policy = "never"` 可能未阻止 escalation request｜2026-08-11

openai/codex issue #37914 的回報者在 VS Code extension 26.803.61601、WSL2、trusted project 中，把 `.codex/config.toml` 設為 `approval_policy = "never"`，再以寫入受保護 `.git` 路徑作 probe；預期 command 在 sandbox 內失敗且不要求升權，實際卻產生 escalation request。回報者也明確說明：這不是已證實的 sandbox bypass，request 仍可能由人或 automatic reviewer 拒絕。

issue 目前開放、帶 `bug`／`extension`／`sandbox`／`config` 標籤，尚無維護者確認。實務防呆是把「是否提出升權」也列入回歸測試，並在 CI／企業政策層驗證 effective config，而不是只看專案檔寫了什麼。[issue #37914](https://github.com/openai/codex/issues/37914)

## 6. 今天值得嘗試

### 做一個 60 分鐘的「Skill 後門 + runtime policy」最小演練

1. 選一個會呼叫工具的非敏感 Skill，記錄來源、版本、checksum 與允許工具。
2. 準備 10 個正常 queries，再加入 10 個看似無害但含品牌名、特殊片語、拼字變體或格式符號的 queries。
3. 在 Skill 文件中逐段停用規則，建立「規則片段 × query」矩陣，找出只有兩者共存才出現的 tool-call 突變。
4. 把敏感工具限制為 explicit allowlist、read-only／dry-run 與固定參數 schema；副作用前要求獨立確認。
5. 保存 trajectory，對 System Prompt、Rule Bank、Memory、Tool Policy 分別歸因；修改後同跑 safety cases 與 benign utility cases，退步就回滾。
