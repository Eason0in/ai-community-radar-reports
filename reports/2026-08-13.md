### 4. `CLAUDE.md` 膨脹可能是「只記得加規則、不敢刪規則」｜2026-08-11

**Catastrophic Remembering** 研究分析 1,867 個 repositories、247,694 段 instruction lifetimes，作者報告 agentic prompt 在生命週期平均成長 226%，每次 commit 淨增 4.9 條 instructions；規則越老越不容易被刪。關鍵不是長文件本身，而是規則的理由消失後，維護者難以證明刪除不會造成 regression。

作者在可驗證環境中加入「說明規則存在理由」的 prompt comments，報告 excess instructions 從 +211.3% 降到 +1.4%，並在 WildIFEval inversion 上讓 instruction following 最多提升 23.1%。同日的 **SkillZip** 則主張把重複規則提升到共同 scope、把重複步驟抽成 procedure、保留例外與完整 contract coverage。兩者都是作者研究結果，但共同訊號很實用：Agent instructions 應像程式碼一樣保留 rationale、owner、適用範圍與刪除測試，而不是只追加 workaround。[Catastrophic Remembering](https://arxiv.org/abs/2608.11095)｜[SkillZip](https://arxiv.org/abs/2608.11079)

### 5. Agent 安全評測應驗證最終狀態，而不是只看模型說了什麼｜2026-08-11

**REDAgentBench** 把 attack exposure、execution、observation 與 adjudication 分開，在隔離 service sandbox 執行 1,661 個案例，並用 service receipts 與 final-state changes 判斷是否真的造成傷害。作者在六個模型、三種 agent harness 上報告 macro-average attack success rate 為 65.69%；在 action anchor 可解析的 confirmed violations 中，近五分之一發生在 Agent 已說出相關限制或風險之後，形成「知道規則、執行仍違規」的 Recognition–Execution Gap。

作者也報告 training-free policy reminder 在 matched replay 中把 confirmed violations 降低超過 70 個百分點。這些仍是作者 benchmark，不能外推到所有 Agent；更值得採用的是量測方式：敏感流程要以外部狀態、不可偽造 receipt 與權限結果判定，而不是用 final answer 自我宣告成功或安全。[論文](https://arxiv.org/abs/2608.10669)

## 3. 新技術、新方法

### A. Prompt／Skill 的每條規則要有「為什麼」與可刪除證據｜2026-08-11

為每條規則記錄來源事件、預防的 failure、適用 scope、owner、加入日期與 regression case。每次整理先合併重複 rule，再把共用 action sequence 抽成單一 procedure；只有在 coverage check 證明 trigger、tool contract、obligation 與例外仍存在後才刪除。這比單純要求 LLM「把文件縮短 30%」更能避免罕見但重要的規則被壓掉。

### B. 長搜尋的記憶要能回滾依賴，不只是改寫摘要｜2026-08-11

**ReTree** 把搜尋記憶做成保存 evidence、bounded summary 與 revision history 的樹；新證據推翻舊 claim 時，回溯到 claim 引入節點、替換證據、重建 summary、剪掉受影響 branches 再繼續。作者在四個 QA／search benchmarks 報告最高提升 25.6 個百分點，仍屬作者結果；可借用的工程原則是讓結論保留 source lineage 與 dependency edges，否則「更新一段摘要」無法修復下游推論。[論文](https://arxiv.org/abs/2608.10676)

### C. Test-time scaling 可檢索「解題步驟」，但別忽略污染與延遲｜2026-08-11

**ThinkRetrieve** 在 reasoning 的每一步，從已解題 corpus 取回相近的 step-by-step exemplars，再注入當前 trace；作者在 1.5B–8B 五個模型、GSM-8K／MATH-500／AIME 2025／SciQ 上報告優於一般 sequential scaling，AIME 2025 相對提升最高 60%。實作前要另外測 retrieval latency、相似題 leakage、錯誤解法污染與 corpus license；「檢索推理方式」比檢索事實更容易把資料集捷徑帶進結果。[論文](https://arxiv.org/abs/2608.10928)

### D. Autoresearch 的浪費常來自 orchestration，而不只模型能力｜2026-08-11

另一篇研究在 tabular modeling pipeline 觀察到 branches 重複解同一 runtime bug、剩餘預算未用於 hyperparameter tuning、tree search 缺乏探索，以及資料分析沒有影響後續決策。作者以跨 branches 共享 runtime constraints 的 global debug consultant、prompt／control 改動與 refined tree search，在固定底層模型下回收部分浪費。部署時可先量 `重複錯誤率`、`未使用預算`、`branch diversity` 與 `分析→決策引用率`，再考慮換模型。[論文](https://arxiv.org/abs/2608.10424)

### IBM Technology｜What Is Context Engineering? Why It Matters for AI Agents

- **發布日期：** 2026-08-11
- **連結：** [YouTube](https://www.youtube.com/watch?v=Qx0fCqpkBus)
- **查核時觀看數：** 12,734；片長 9:56。
- **內容依據：** 已下載並完整閱讀人工英文字幕；定義與細節以 IBM 同主題文章交叉核對。

**快速摘要：** 影片把 prompt engineering 定位成 context engineering 的一部分：Agent 的輸入環境還包含 system prompt、使用者請求、RAG 文件、對話 history、API／tool outputs 與其他 agents 的結果。核心不是把 2M tokens 塞滿，而是維持 relevance、structure、timing、compression，再持續管理 retain／discard、priority、freshness 與 consistency。

**內容重點與時間點：**

- **0:00–2:30：** 定義 context engineering，說明多步 Agent 會 reason、用工具、檢索與更新 memory，因此只調 prompt wording 不夠。
- **2:30–3:59：** 大 context window 不保證更好；無關、未結構化或缺漏資訊可能增加 confusion 與 hallucination。
- **3:59–5:49：** context 包含 system prompt、query、retrieved documents、history、tool／API／agent outputs；好的 context 要 relevant、structured、just-in-time、compressed。
- **5:49–7:38：** context management 要決定保留／丟棄、維持 continuity、依 relevance／recency／importance 排優先、更新或 invalidate 舊資料。
- **7:38–9:45：** 以醫療預約 Agent 示範把 clinic policy、doctor availability、patient preferences、相關病史與 scheduling API slots 組成結構化 context。

**教學／工作流程：** 列出 decision 所需資料 → 區分 system rule、user intent、retrieved knowledge、live state 與 tool output → 對每類設定 relevance／freshness／authority → 在需要時才注入 → 壓縮但保留 provenance → 執行前檢查 policy 與 current state → 事後更新或失效 context。

**涉及工具／模型／功能：** LLM／AI agents、system prompt、RAG、vector database／document store、conversation history、API／tool outputs、context processing、context management。

**作者心得：** context window 像有限 working memory；品質與結構比單純資料量重要，尤其 Agent 要跨多步更新資訊與採取動作。**優點：** 概念邊界清楚，能把「多塞文件」重新拆成資料生命週期與執行時選擇。**缺點／限制：** 沒有程式碼、architecture、量化 benchmark、retrieval evaluation、prompt-injection defense 或醫療合規細節；「更完整 context 就不再 guessing」是教學簡化，高風險系統仍需 deterministic validation、authorization 與 human review。[IBM Context Engineering](https://www.ibm.com/think/topics/context-engineering)

**適合對象：** 正從單輪 chatbot 轉向 RAG／Agent 的產品、資料與平台團隊。**是否值得看完整影片：** 值得當 10 分鐘共同語言；熟悉 RAG 的讀者可直接看 3:59–9:45。

**可立即嘗試：** 對一個現有 Agent 建六欄 context inventory：`來源`、`用途`、`authority`、`freshness TTL`、`注入時機`、`失效／刪除條件`。先移除一項低 relevance、無 provenance 或過期資料，再用固定案例比較正確率、tool-call success、token 與 latency。

### 做一次 45 分鐘的「instructions 去膨脹 + 可讀輸出」小實驗

1. 選一份現有 `AGENTS.md`／`CLAUDE.md`／Skill，標出重複規則、沒有理由的規則與只有例外但沒有主流程的段落。
2. 為每條保留規則補 `why`、來源 failure、scope、owner 與 regression case；相同 requirement 只留一個 canonical rule。
3. 把重複 action sequence 抽成一個 procedure，以 reference 取代複製；不要刪除 unique exception。
4. 同時做一個只規定「outcome、verification、risk、next step」的 output style，若仍需 coding，確認保留內建 coding instructions。
5. 用 5 個正常任務、2 個 edge cases 跑新舊版本，記錄 instruction misses、input／output tokens、人工閱讀時間與錯誤核准次數；只有 coverage 不退步才換新版。
