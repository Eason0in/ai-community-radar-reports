### 4. 新研究提醒：Agent Skill 可能提升能力，也可能穩定地把模型帶錯方向

- **論文提交日期：2026-08-12**
- 《Agent Skills Can Be Harmful》以「有 Skill／無 Skill／語意相近 Skill」做差分比較，在 SkillsBench 與 SWE-Skills-Bench 找到 307 個 Skill 誘發失敗：125 個功能錯誤、182 個效率退化。
- 作者觀察到，即使 Skill 與任務相關，也可能造成錯誤實作、遺漏需求、過度驗證或沉重流程；效率損失不只來自提示變長。這代表安裝 Skill 不等於得到能力，必須對同一任務做成對評估，並把成功率、token、工具呼叫與不必要步驟一起量測。
- 這些數字是作者在指定基準與設定下的研究結果，不宜直接外推到所有 Skill、Agent 或實際專案。
- 原始來源：[arXiv｜Agent Skills Can Be Harmful](https://arxiv.org/abs/2608.11888)

### 5. Agent 可靠性評測開始從「答對」轉向「衝突指令與工具故障時仍能做對」

- **論文提交日期：2026-08-12**
- Harness-IF 建立 60 個多輪程式任務、642 條規則庫與五種指令載體。作者測得 12 個前沿模型的一般準確率為 72.1%～85.9%，但需要違反既有慣例才能遵循的新規則，表現再低 3.6～7.4 個百分點。
- BENCH2ROBUST 則把暫時性、持續性與靜默工具故障注入 Agent 工作流，要求模型明確決定重試、切換或停止；作者報告 Bayesian Tool Memory 在未重新訓練下，於保留的 Retail 任務最高提升 16.8 個百分點。
- 共同訊息是：不能只測正常路徑。專案層規則、工具描述、重試上限、替代工具與停止條件，都應進入同一套可重現測試。
- 原始來源：[arXiv｜Harness-IF](https://arxiv.org/abs/2608.11727)、[arXiv｜Retry, Switch, or Abstain?](https://arxiv.org/abs/2608.11977)

## 3. 新技術、新方法

### 方法一：Skill 採「成對基準」而不是只看展示成功案例

1. 固定同一模型、提示、工具與資料，先跑沒有 Skill 的基準。
2. 加入目標 Skill，再加入一個語意相關但非目標的對照 Skill。
3. 同時記錄任務成功、規則遺漏、工具呼叫數、token、延遲、重試與人工修正。
4. 把「過度驗證、無必要 pipeline、錯誤停止條件」列為明確失敗類型。
5. 只有在多次重跑仍有淨效益時，才把 Skill 設為預設流程。

這套做法直接對應《Agent Skills Can Be Harmful》的差分設計，也能避免把一次漂亮示範誤當成穩定能力。

### 方法二：把指令遵循測試拆成「順著慣例」與「違反既有慣例」

Harness-IF 的 Against-Prior Accuracy 很實用：例如專案明確規定「不要自動格式化」或「只能改指定檔案」時，測試模型是否真的依新規則行動，而不是剛好做出平常偏好的結果。建議至少覆蓋 system、專案檔、使用者訊息、工具描述與 Skill 五個載體，並加入彼此衝突的案例檢查優先序。

### 方法三：工具政策要明寫 retry、switch、abstain

對每個外部工具定義：哪些錯誤可重試、最多幾次；何時切換替代來源；何時停止並交還使用者。BENCH2ROBUST 的結果顯示，保存工具可靠度的歷史訊號有機會提升故障下的決策，但論文結果仍需在實際服務的速率限制、權限與成本條件下驗證。

### 方法四：RAG 評測要看「全部要求同時滿足」

- **論文提交日期：2026-08-12**
- EnterpriseRAG 收錄 983 個專家驗證樣本，涵蓋六個企業領域，刻意加入檢索雜訊、知識缺口、事實衝突與複雜指令。
- 作者測試 13 個模型，個別限制的平均遵循率約 80%，但所有要求同時滿足只有 26.8%，形成約 57 個百分點的協調落差。這是作者基準結果，但很適合提醒團隊：答案引用正確，不代表格式、拒答條件、衝突處理與完整性也同時正確。
- 原始來源：[arXiv｜EnterpriseRAG](https://arxiv.org/abs/2608.11584)

### 5.2 IBM Technology｜5 Best Practices for Building AI Agent Skills

- **發布日期：2026-08-10｜查核觀看次數：30,709｜片長：13:22**
- 連結：[YouTube](https://www.youtube.com/watch?v=qYNs80FKIVc)
- **快速摘要：** 影片提供一套由實際作業經驗提煉 Skill 的流程：描述要寫清楚「做什麼、何時用」、把真正的 gotcha 變成指令、用 progressive disclosure 控制 context，並將脆弱且需精確重複的步驟改成可驗證的程式。

**內容重點**

1. `00:00–01:27` 將 Skill 定義為可被 Agent 載入的程序知識，也提醒 Skill 內的程式碼可能接觸檔案、網路與憑證。
2. `01:29–03:40` 建議 description 明寫 `what` 與 `when`，加入可觸發的任務語彙；Agentskills.io 規格確認 name 最長 64 字元、description 最長 1,024 字元。
3. `03:42–06:17` 從人工實作、報告、runbook、review comments 與 PR 回饋中抽取真正的修正與例外情況，而不是只生成泛用清單。
4. `06:21–07:55` 建議主 `SKILL.md` 控制在 500 行／約 5,000 tokens 內，詳細資料移到 references，依需要才載入；官方最佳實務文件也有相同建議。
5. `07:57–10:41` 將精確、易錯、需重複的步驟寫成 deterministic script；較具判斷空間的部分保留成文字指令，並為 script 加入輸入驗證與測試。
6. `10:43–12:24` 提醒第三方 Skill 應視同軟體供應鏈，先審查程式、外部依賴、網路存取與 secrets。影片引用的 Snyk 掃描在 3,984 個 Skill 中發現 36.82% 至少一項問題、13.4% 為 critical；這是資安廠商針對特定來源、依其規則產生的結果，不是整個生態系的獨立盛行率。
7. `12:24–13:22` 回顧五項準則，核心是「由真實專業知識出發、節省 context、讓脆弱步驟可重現、第三方內容先審查」。

**教學／工作流程**

1. 先由熟悉工作的人完整手做一次任務，記錄錯誤、修正、例外與驗收條件。
2. 將可觸發的任務與使用時機寫進 description，而非只寫模糊能力名稱。
3. 主檔只保留決策與必要步驟，長文件移到 references，註明載入時機。
4. 把精確轉換、計算、格式驗證或批次操作寫成 script，為其加入測試與失敗訊息。
5. 安裝外部 Skill 前，檢查來源、雜湊、依賴、檔案／網路／金鑰權限，並在隔離環境試跑。
6. 最後以「有 Skill／無 Skill」的相同任務做成對評估，補上影片沒有深入示範的品質門檻。

**涉及工具／規格：** Agent Skills、`SKILL.md`、references、deterministic scripts、Claude Code／Codex 類型的 Agent 工作流、Snyk ToxicSkills 研究。

**作者心得：** IBM 講者主張 Instruction 適合有彈性的步驟，Code 適合脆弱而需精確重複的步驟；最有價值的 Skill 內容通常是專家實作時才知道的 gotcha。

**優點：** 步驟具體、涵蓋 context 成本與供應鏈風險，並能直接轉成 Skill review checklist。

**缺點與限制：** 沒有完整程式專案示範；不同 Agent 對觸發與指令優先序的實作仍可能不同；deterministic script 本身也可能有錯，仍需 sandbox、測試與權限最小化。

**適合對象：** 正在建立團隊 Skill、runbook 自動化或審查第三方 Agent 擴充套件的工程師。

**是否值得看完整影片：** 值得，尤其是 `01:29–12:24`；內容精簡且能直接採用。

**贊助標示：** 未發現第三方贊助揭露；屬 IBM 品牌教學內容，含 IBM 電子報／指南宣傳。影片說明標示逐字稿與 metadata 有使用 AI。

**立即可試：** 挑一個現有 Skill，今天完成六項稽核：重寫 `what/when`、補三個真實 gotcha、移出長篇 reference、為一個脆弱步驟加 validator script、盤點網路與 secrets 權限、用相同任務跑一次無 Skill 對照。

**官方／原始資料交叉查證：** [Agent Skills Specification](https://agentskills.io/specification)、[Agent Skills Best Practices](https://agentskills.io/skill-creation/best-practices)、[Snyk｜ToxicSkills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)、[arXiv｜Agent Skills Can Be Harmful](https://arxiv.org/abs/2608.11888)。格式限制與 progressive disclosure 有規格／官方最佳實務支持；安全比例是 Snyk 廠商研究，新論文數字則是作者研究結果。

## 6. 今天值得嘗試

### 45 分鐘「同任務、成對、帶故障」Agent 驗收

1. 選一個 10～15 分鐘能驗收的真實任務，固定輸入、資料版本與成功條件。
2. 先跑現有模型／無 Skill 基準，再只更換新模型或加入目標 Skill。
3. 各加入一次暫時錯誤、持續錯誤與「看似成功但回傳內容缺漏」的工具情境。
4. 要求 Agent 在 retry、switch、abstain 之間明確選擇，設定重試上限。
5. 用 deterministic validator 檢查輸出及外部狀態；跨 Agent 分工另要求接收端 acknowledgement。
6. 記錄完整成功率、規則遺漏、token、延遲、費用、重試與人工修正。只有在整體指標改善時才採用，不以單次漂亮輸出或廠商榜單決定。

這個小實驗同時覆蓋今天四個關鍵訊號：更快的新模型、Skill 可能造成的反效果、違反既有慣例時的遵循落差，以及工具成功訊號不等於端到端成功。
