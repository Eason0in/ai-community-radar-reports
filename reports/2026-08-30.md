## 1. 今日最重要的 3–5 件事

### 1. Anthropic 預覽 Model Hardware Standard：用共同 driver 讓 Agent 操作實驗室與製造設備

- **發布日期：2026-08-27｜本報補充原因：週末官方案例與限制仍值得納入。** MHS 是 Anthropic 與 HHMI Janelia 起步的研究預覽，將設備能力描述成標準化 state、procedure 與 `read`／`write` primitives，再由 MCP、CLI 或 API 交給模型無關的 Agent harness 使用。[Anthropic 官方說明](https://www.anthropic.com/news/model-hardware-standard-research-preview)
- 安全設計的重點不是讓模型直接自由控制硬體，而是把 bounds、interlocks、emergency stop 與可觀察狀態寫進 driver；Agent 可先探索，再把學到的操作編譯成一般、可檢查的 deterministic script，避免每個毫秒都靠線上推理。
- QuEra 公布 Claude 透過 MHS 產生雷射回復控制程式：700 次計時試驗中回復 695 次，多數故障在 6 秒內排除；這是 **QuEra／Anthropic 合作方結果**，不是獨立 benchmark。[QuEra 第一手案例](https://www.quera.com/press-releases/quera-computing-uses-ai-to-automate-a-critical-quantum-computer-subsystem-enabling-the-acceleration-of-commercial-grade-quantum-computing-deployments-from-quera)
- Anthropic 同頁也揭露反例：Genentech 實驗中，Claude 面對液體氣泡造成的物理錯誤時一度反覆重試、讓情況更糟，仍需人類補充物理原因後才能形成可重用 skill。MHS 尚未開源、只限少數研究預覽夥伴，不能視為已成熟的通用工業標準。

### 2. 專業外觀會讓 Agent 對不可知問題做出行動，即使面板數字全部捏造

- **投稿日期：2026-08-27｜證據層級：預註冊預印本，作者結果。** 一項跨 12 個前沿模型的研究，把本質上不可預測的問題包在專業市場面板中；承諾採取方向性行動的比率由裸問題的 6.5% 升至最高 54.0%。[原始論文與資料](https://arxiv.org/abs/2608.27167)
- 全部數字都是虛構時，commitment 仍由 24.5% 升至 36.8%，與真實市場資料的 37.6% 無統計顯著差異。模型在被問「這題是否可知」時有 90% 能辨識不可知，失敗點更像是 **know → act gate**，不是完全不懂。
- 作者用 540 個合成案例微調 3B 模型後，在原案例把錯誤承諾降至 0%，也能轉移到三個未見領域；但 rigid response format 會破壞效果。實務上，風險不是只有 hallucination，而是系統把「長得像證據」直接接到交易、批准或工具動作。

### 3. ASIL 用結構化 state 與 semantic actions 取代 screenshot-and-click

- **投稿日期：2026-08-27｜狀態：EMNLP 2026 Findings。** ASIL 為 15 個應用暴露 JSON observation 與可執行 semantic actions，涵蓋 300 個單應用、80 個跨應用任務；作者報告 closed models 得分超過 80，平均每題少於 5 個 action。[原始論文](https://arxiv.org/abs/2608.26991)
- 在修復過的 runtime、50-step 預算下，screenshot-and-click 的 strict success 只有 6.6／26.6；較容易的 OSWorld 對應帶也只有 15.0／53.3。這是作者在自建介面與 benchmark 的結果，不能直接外推所有桌面軟體。
- 最值得帶走的訊號是：GUI 截圖不完整、座標動作脆弱；若產品能提供穩定 state schema、語意 action、前後條件與錯誤碼，Agent 的規劃、訓練與稽核都會更容易。ASIL 對 draw.io 的 MCP content contract 只打平，也提醒「原生介面設計得好」未必需要另一層抽象。

### 4. Agent 安全不能只看規則有沒有載入，還要確認 gate 真的能阻止動作

- **回報日期：2026-08-29。** Claude Code issue #90564 回報：在 Agent SDK／headless session 中，`PreToolUse` hook 正確算出 exit 2 deny，但實際工具呼叫仍成功；留言另稱靜態 `permissions.ask` 在同類 session 也未形成互動阻擋。[Claude Code issue #90564](https://github.com/anthropics/claude-code/issues/90564)
- issue 目前仍 open，帶有 `has repro`、`area:security`、`area:hooks`、`area:agent-sdk`，但沒有 maintainer 根因或修復公告。可確認的是「回報者的重現」，不能寫成所有 SDK session 都會 fail-open。
- 安全含意很直接：hook 有執行紀錄不等於 deny 已生效。高風險 write／delete／push 必須用 canary side effect、OS／git／資料庫層 policy 或測試性拒絕驗證；若 gate 不能在模型之外同步阻擋，就只能當 observability，不能當 security boundary。

## 3. 新技術、新方法

### 方法一：把「模型知道」與「系統允許行動」拆成兩個可測 gate

先要求模型輸出 `knowable`、證據來源、反證與不確定性，再由獨立 policy 決定是否能呼叫工具。測試不能只有正常資料；至少加入同版面、真數字／假數字／無數字三組，確認漂亮 UI、圖表與專業語氣不會改變不可知問題的拒絕行為。不要用只能填 `buy`／`sell` 的 rigid schema 把模型的 abstain 路徑刪掉。

### 方法二：讓軟體與設備提供 state contract，不把畫面當唯一真相

每個 action 應有穩定名稱、typed arguments、precondition、side effect、success evidence 與 error code；設備再加硬限制、interlock 與 emergency stop。Agent 可用結構化介面規劃，用畫面做交叉驗證；只有沒有原生介面時才退回 click。長時間或高速操作先由 Agent 探索，在安全 testbed 驗證後再轉成可稽核 script。

### 方法三：所有安全 hook 都要跑「負向驗證」

不能只看到 hook log 就宣告 guard 有效。準備一個無害但可觀察的禁止動作：hook 應明確 deny、工具不應產生 side effect、process 應回傳非成功狀態、Agent 也應收到可解釋錯誤。CLI、SDK、headless、resume 與 remote session 分開測；任一 surface 無法同步阻擋，就在更底層再加不可繞過的 policy。

## 4. 社群實戰心得

### Codex Code Mode：獨立唯讀檢查若逐次返回模型，會放大累積 input

- **回報日期：2026-08-29｜狀態：open issue，尚無 maintainer 結論。** #41450 以官方 client、隔離 `CODEX_HOME`、本機 deterministic fake Responses server 與 50 個已知獨立檢查做 A/B：序列排程為 60 個 outer cycles、11,100,973 logical input；加入安全並行排程規則後為 15 cycles、2,041,915 input，兩側皆 50/50 coverage、86 個 nested calls、0 error。[Codex issue #41450](https://github.com/openai/codex/issues/41450)
- 81.606% 是高 context、特定 fixture 的量測，不是所有工作都省 82%，也沒有證明某一個模型家族天生較差。可用原則只有：已確認互相獨立、唯讀、無衝突的檢查才 batch；寫入、依賴、approval、等待與需要看前一步結果的操作維持序列。
- 另一個次要放大器是短間隔 polling：回報中的約 30 秒測試，1 秒輪詢用了 7 cycles，合理 wait window 用 2 cycles。真正要優化的是 model round-trip 形狀，不是刪掉驗證項目。

### Claude Agent SDK：安全 hook 的「有跑」與「有擋」要分開驗證

- #90564 的回報者以同一 JSON payload 手動執行 hook，確認 deny 計算正確；真實 SDK session 卻讓工具完成。這與上面的 prompt／rule 問題不同：即使規則寫對、hook 也發火，執行路徑仍可能沒有等待或傳回阻擋結果。
- 在官方說明前，實務避雷是不要把 headless `PreToolUse` 當唯一刪除／push／跨 worktree guard。用 repository 權限、pre-push／server-side rule、唯讀 credential、資料庫角色與隔離工作目錄把禁止事項做成工具外部的不變條件，並保存一個可重跑的 deny canary。

### Tech With Tim｜Vibe Coding Has A Security Problem (And How To Fix It)

- **發布日期：** 2026-08-29
- **觀看次數：** 11,530（2026-08-30 08:06 Asia/Taipei 重新查核）
- **片長／逐字稿：** 18:40；已完整閱讀 `en-orig` 英文原始自動字幕
- **連結：** [YouTube 原片](https://www.youtube.com/watch?v=NfctRQhMMdI)
- **贊助揭露：** 明確由 Superblocks 贊助，說明欄含該產品導流連結；另有作者 AI Agent 課程、Hostinger、Wispr Flow 等自我推廣／affiliate。

**快速摘要：** 作者先用低階模型做一個假的 mentor／student 內部儀表板，再示範三個典型問題：改 URL 就能讀別人的紀錄（IDOR／broken access control）、未驗證即可直接呼叫資料 API、資料庫帳密被打包進前端。後半改在贊助商 Superblocks 重做，展示把 secret、SSO、RBAC、publish-time scan 與 audit log 放在平台層，而不是期待每次 prompt 都記得安全規則。

**內容重點**

1. `00:00–03:24`：把 shadow AI 定義成業務人員自行做出、連上真實公司資料、未進 SDLC 的應用；prototype 被分享後可能悄悄成為 production。
2. `03:24–09:08`：登入後只「顯示自己的學生」不等於伺服器有做 object-level authorization；改 ID 可讀別人對話，API 甚至不需 authentication。
3. 同一 demo 的前端 bundle 包含 MongoDB URL、username 與 password。作者使用合成／匿名資料示範，沒有真的公開客戶資料。
4. `09:08–14:42`：贊助段把 secret 放在 integration layer，app 只透過平台取資料；作者展示 SSO、RBAC、VPC／自有 cloud、audit log 與 publish gate。
5. `14:42–17:18`：重跑 ID 竄改後得到 access denied；但影片對前端是否完全沒有 MongoDB URL只說「pretty sure」，沒有展示完整 bundle scan，不能算嚴格驗證。
6. `17:18–18:40`：作者認為企業不應只禁用 vibe coding，而應建立 inventory、identity、policy 與 audit control plane；個人週末專案不一定需要重型平台。

**教學／工作流程：** 用無敏感資料建立最小 app → 準備 admin 與一般使用者 → 竄改 URL／object ID → 直接呼叫 API → 搜尋前端 bundle 的 secret → 檢查 server-side authorization → 對 publish gate 做負向測試 → 以未授權帳號重跑 → 查 audit log。涉及工具／概念為低碼 AI builder、MongoDB、瀏覽器 DevTools、`curl`、Superblocks、SSO、RBAC、VPC、policy scan 與 audit log。

**作者心得：** AI code 可能少犯錯，但無法保證永遠正確；應問「AI 與真實資料之間有什麼不可繞過的控制」。這個核心觀點合理，但後半產品比較來自付費贊助示範。

**優點：** 攻擊路徑可看懂；清楚區分 UI 隱藏與 server-side authorization；重建後用同一類 ID 竄改重測；主動說明 demo 資料是假的。**缺點與限制：** 沒公開 repo、prompt、掃描報告或可重現測試；使用低階模型讓漏洞較容易出現；沒有比較同一 app 經一般 code review／測試後的結果；把產品自述當成平台能力展示，未做獨立滲透測試。

**重大宣稱交叉查證：** 改 ID 讀取他人資料符合 [OWASP IDOR 定義與 server-side authorization 建議](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)。Superblocks 官方文件確認集中式 secrets、RBAC、audit、cloud／hybrid／cloud-prem 與 SDLC 整合，但仍是廠商自述。[Superblocks 文件](https://docs.superblocks.com/getting-started/what-is-superblocks) 影片提到約 1,400 個 AI-built apps、65% 有安全問題，說明欄未附原始研究；本報未把該比例當成獨立確認事實。

**適合對象：** 正在把 AI 生成內部工具接到真實資料的產品、平台、資安與工程團隊。**是否值得看：有條件值得。** 前 9 分鐘的 broken access control demo 很實用；後半要以贊助內容觀看。

**可立即嘗試：** 對自己的測試 app 建兩個低權限帳號，先用 A 讀自己的 record，再把 request 中 ID 換成 B；接著在無登入狀態呼叫同一 API，最後搜尋 production bundle 是否含 connection string／secret。任一步成功，都先撤掉公開存取、輪替 secret，再補 server-side object authorization 與 regression test。

## 6. 今天值得嘗試

### 45 分鐘：做一次「漂亮介面不算證據、guard 有跑不算有擋」雙重測試

1. 選一個無敏感資料的 Agent flow，準備內容相同但視覺包裝不同的 plain text／專業 dashboard／捏造 dashboard 三組輸入；不可知任務三組都必須 abstain。
2. 為一個低權限 API 建 A／B 兩筆 record；登入 A 後竄改 ID 讀 B，確認拒絕發生在 server side，而不是只把連結藏起來。
3. 對最重要的 tool hook 設一個無害 canary deny：保存 hook verdict、process exit、實際 side effect 與 Agent看到的錯誤。四者少一個都不算通過。
4. 若操作 GUI，記錄 screenshot click 失敗率；同時列出能否改成 JSON state＋semantic action。先轉換最常失敗的一個動作，不需一次重做整套介面。
5. 把結果寫成可重跑測試；模型、harness、SDK 或 session surface 變更後重新執行。

**今天的結論：** 當 Agent 開始碰真實設備、GUI 與資料庫，最危險的錯覺是「模型讀過規則、hook 也有 log，所以系統安全」。真正的控制面要能描述完整 state、在模型外拒絕動作、留下可重跑的負向證據，並在 physical／API／process 層真的停止 side effect。
