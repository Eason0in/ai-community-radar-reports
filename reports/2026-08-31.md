### 1. OpenAI 預告終止向 Cursor 提供模型：供應依賴成為產品風險

OpenAI 於 8 月 28 日表示，已通知 SpaceX，計畫結束向 Cursor 提供 OpenAI 模型，提議的停止日期為 2026 年 11 月 12 日，且未來模型也不再供 Cursor 使用。Cursor 則在 8 月 14 日公告已被 SpaceX 收購，並把 GPU 資源與 Grok 整合列為後續方向。OpenAI 文中的合約與信任疑慮是其單方說法，目前不應擴寫成已由第三方證實的事實。

這件事對團隊的直接提醒不是選邊站，而是把「模型供應商可否突然退出」納入產品設計：盤點每個 AI 功能實際依賴的模型、匯出提示詞與評測集、預先定義替代模型及降級模式，並為切換建立可重跑的品質門檻。

來源：[OpenAI 官方說明](https://openai.com/index/our-decision-on-cursor-following-its-acquisition-by-spacex/)｜[Cursor 收購公告](https://cursor.com/blog/joining-spacex)

### 3. CorporateBench：企業知識問答不能只用小型、靜態文件集評測

CorporateBench 建立四家合成企業，規模從 12 人到 10,000 人，包含超過 23 萬份、會隨時間演進的文件，再由人工驗證多任務問答。作者對五個 LLM 系統的測試顯示，資料規模與企業現實度上升時，表現會明顯惡化。這是 EMNLP Findings 論文與合成資料基準，不等於真實企業部署的最終排名；但它補出一個常被忽略的失敗面：原型在十幾份文件上正確，不代表能處理跨部門、版本衝突與時間條件。

來源：[CorporateBench 論文](https://arxiv.org/abs/2608.27391)

### 4. 71 萬筆企業提示詞研究：職級與使用方式相關，一次訓練的效果未持續

一項 KPMG 後勤職能研究分析 3,925 名員工、八個月共 713,564 筆提示詞，以提示清晰度、策略使用與用途多樣性作為「成熟度」代理指標。成熟度隨職級上升；訓練當月有短暫增加，但資料未顯示持續改善。這些指標不是輸出品質或生產力，研究也不能證明訓練無效；較穩健的解讀是：若沒有嵌入實際工作、回饋與複習，單次課程很難留下可觀測的長期行為改變。論文使用 KPMG 內部資料，並揭露作者的 KPMG 關係。

來源：[Sophistication in Generative AI Use](https://arxiv.org/abs/2608.27364)

## 三、研究／實作方法整理

### 方法 A：把評測切成「小型、部門、企業」三個尺度

不要只測十份乾淨文件。至少建立三層資料量，加入同名文件、修訂版、跨部門權限與「截至某日期」的答案；每次改模型、切分或檢索器都重跑同一組題。記錄答案、引用、延遲與成本，才能看見擴大規模後的退化，而不是只看平均正確率。

### 方法 B：把 AI 訓練改成間隔練習與工作內回饋

用真實但去識別化的任務，設計每週短練習；保存「原提示、修改、輸出、採用／退回理由」，兩到四週後用相同標準複測。KPMG 研究的代理指標可當觀察線索，但不要把提示較長或策略較多直接等同於工作成果。

### 方法 C：先做簡單提示詞最佳化，再決定是否導入複雜搜尋

Naive Prompt Optimization 以單一路徑、教師模型回饋與 rollout 反覆修訂提示詞，作者報告在部分任務能以較少 rollout 接近或超過更複雜方法。實務上可先用固定訓練集迭代、獨立保留集驗證並保留回退版本；若提升只出現在同一批題目，就不應上線。這仍是新預印本，結果需在自己的模型與資料上重現。

來源：[Naive Prompt Optimization](https://arxiv.org/abs/2608.27266)

## 四、社群洞察與真實案例

### Codex Windows Desktop：封裝環境可能讓 AppData 指向另一份檔案

一則 8 月 30 日建立的 Codex 開放議題指出，Windows Desktop MSIX 在 `danger-full-access` 下存取 `%APPDATA%` 時，最終路徑可能落到套件的 `LocalCache/Roaming`，與一般終端機看到的檔案不同；回報者以最終路徑與 SHA 雜湊比對出差異。議題已有可重現資訊，但尚無維護者確認根因。

可採取的動作：桌面版讀不到 CLI 登入或設定時，先比較 `GetFinalPathNameByHandle`／實際檔案雜湊與一般終端機結果，不要立刻重登或覆寫設定。

來源：[openai/codex #41665](https://github.com/openai/codex/issues/41665)

### Claude Code 長篇圖片工作：舊圖片逐出後可能造成提示前綴反覆失效

另一則 8 月 30 日議題回報，在長篇 PDF 圖片分析中，舊圖片被逐出後提示前綴改變，快取讀取下降，後續每張圖都重新快取大量內容。回報者在完整頁面測試中穩定重現，但尚未以最新版重新測試，也沒有官方根因結論。

可採取的動作：把長篇圖片稽核拆成有界工作階段、優先裁切必要區域、觀察 cache read／write 與 token 成本；不要把單一回報直接推論成所有版本都受影響。

來源：[anthropics/claude-code #90716](https://github.com/anthropics/claude-code/issues/90716)

### 影片 1：Building AI Agents in Pure Python - Beginner Course

- 頻道／日期／觀看：Tech With Tim｜2026-08-30｜約 25,000 次（截點時）
- 連結：[YouTube](https://www.youtube.com/watch?v=c9AnqCeyxbI)
- 摘要：以 Python 與 OpenAI SDK 手刻「模型＋工具＋迴圈」代理，逐步做出可讀寫檔案、列目錄與執行指令的迷你程式代理。
- 核心觀念：模型只提出工具呼叫，真正執行工具的是應用程式；訊息歷史提供短期狀態；工具 schema 是模型與程式間的合約；終止條件必須由外層迴圈控制。
- 工作流程：定義工具 → 把工具描述交給模型 → 接收零個或多個工具呼叫 → 程式執行 → 回傳工具結果 → 重複直到完成。
- 工具／模型：Python、`uv`、OpenAI SDK、Chat Completions、手寫函式工具；影片口述使用 GPT-5 mini。
- 優點：從零開始，清楚呈現工具執行權仍在程式端；約 37 分鐘即可理解最小代理骨架。
- 限制：示範直接執行 subprocess，缺少路徑邊界、指令允許清單、最大步數、成本上限與完整寫入核准；API key 流程也不宜照抄到正式環境。OpenAI 官方文件建議使用環境變數、嚴格工具 schema，並處理零／一／多個工具呼叫；Responses API 另提供對話狀態與工具呼叫上限。
- 適合誰：想理解代理迴圈、但還沒看過工具呼叫完整生命週期的 Python 開發者。
- 是否值得看：值得當入門教材；安全控制要自行補齊，不能直接視為生產範本。
- 立即可試：把檔案工具限制在暫存目錄，為寫入與 shell 各加明確核准，再設定 10 步上限與一組回歸題。
- 商業揭露：影片約 11:50～13:13 有明確 HubSpot 贊助段落；同時導流作者的免費社群與程式碼資源。

交叉核對：[OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling)｜[Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)｜[API Quickstart](https://developers.openai.com/api/docs/quickstart)

### 影片 2：How They Fixed AI's Biggest Local Hardware Problem (with FreeToken)

- 頻道／日期／觀看：Better Stack｜2026-08-29｜約 69,000 次（截點時）
- 連結：[YouTube](https://www.youtube.com/watch?v=8n4Uo47CadY)
- 摘要：介紹 FreeToken 如何讓超出 VRAM 的 MoE 模型保留在系統 RAM，把熱門 expert 當成 GPU LRU 快取，並依記憶體頻寬決定 cache miss 由 CPU 或 GPU 執行。
- 核心觀念：完整權重留在 RAM；GPU 只快取常用 expert；prefill 以雙緩衝重疊傳輸與計算；q* 策略依 CPU／GPU 與 PCIe 狀況選路；FTW 格式為串流權重調整配置。
- 實測流程：在 RTX 5090 32GB、64GB DDR5 上跑約 38GB 的 Qwen MoE 任務，比較 Ollama 與 FreeToken；影片單機結果約從 58 tokens/s 提高至 132 tokens/s。把快取從 58% 降到 40% 時只小幅退化，低於約 20% 後明顯下降。
- 關鍵限制：當 4-bit 模型可完整放進 VRAM，影片中 Ollama 反而約 240 tokens/s、FreeToken 約 225 tokens/s；因此價值集中在 MoE 權重超出 VRAM 的情境。桌面程式目前以 Windows／Linux 為主，影片也遇到專案目錄與檔案修改限制。
- 工具／模型：FreeToken、Ollama、Qwen MoE、RTX 5090；官方專案採 Apache-2.0。
- 作者觀點與證據邊界：影片認為軟體分層能延長消費級硬體壽命；但單一硬體、單一任務不能代表所有模型。論文與專案宣稱涵蓋更多模型及硬體，仍屬作者結果與預印本，需自行重現。
- 適合誰：想在單機跑超出 VRAM 的大型 MoE，且願意量測 RAM／PCIe／GPU 瓶頸的開發者。
- 是否值得看：若模型本來放不進 VRAM，值得；若量化後已完整進 VRAM，先維持較簡單的推論堆疊。
- 立即可試：固定模型、量化、prompt 與輸出長度，分別測 20%／40%／60% GPU 快取，記錄首 token、tokens/s、RAM、VRAM 與答案一致性。
- 商業揭露：未見外部付費贊助口播；片頭有 Better Stack 自有品牌露出，應視為頻道自我宣傳。

交叉核對：[FlashML-org/FreeToken](https://github.com/FlashML-org/FreeToken)｜[FreeToken 論文](https://arxiv.org/abs/2608.16157)

## 六、今天值得試的實驗／方法／提示詞

### 45 分鐘「依賴與規模壓力測試」

1. 列出一個目前最重要的 AI 工作流程：模型名稱、供應商、工具、登入與資料出口。
2. 指定一個替代模型與「模型完全不可用」的降級模式；把硬編碼模型名稱找出來。
3. 用同一題建立 10 份、1,000 份與含版本衝突的文件集，要求答案附引用與時間條件。
4. 若流程能寫檔或執行 shell，加入工作目錄邊界、允許清單、寫入核准、最大步數與成本上限。
5. 保存答案、引用、延遲、token 與成本；只有替代方案達到事先設定的門檻才算可切換。

可直接使用的提示詞：

```text
你是切換風險稽核員。只能根據提供的文件回答，必須列出引用與文件日期。
若文件互相衝突，先指出衝突，再以指定截止日當時有效的版本作答。
資訊不足時輸出「無法由現有證據判定」，不得補猜。
最後以 JSON 回傳：answer、citations、conflicts、as_of_date、confidence。
```

## 結論

今天最值得帶走的不是又多一個模型，而是三個工程動作：為供應中斷準備可驗證的替代路徑、在企業尺度與時間版本下重跑評測、把代理與長篇多媒體任務的執行邊界及成本可視化。能匯出、能回退、能重跑，才是真正可持續的 AI 工作流程。
